# Lapidary

変更を commit できる状態まで仕上げる。観点を通し、直す価値のある不足と過剰を直してから次へ渡す。目的は指摘を挙げることでも、拾ったものを全部直すことでもなく、commit できる状態にすること。

## 手順

1. `git status -sb` と `git diff`（staged があれば `git diff --staged` も）で変更の全体を読む。
2. 観点 6 つを全部通す。各観点の `確認` をやり、何を確認して何が無かったかを持つ。
3. 拾ったものを、直す前と報告へ載せる前に「過剰さ」の基準へ当て直す。観点が検出するのは不揃いと欠落で、直す価値があるかは別の判定になる。「これは誰のどの判断に効くか」に答えられないものは落とす。答えられないまま載せると、判定を読み手へ投げたことになる。自分の変更の範囲外だという理由は、この判定を免除しない。
4. 残った指摘を直す。直す対象は自分が加えた変更に限る。ユーザー自身が編集した箇所と、`CLAUDE.md` の停止線に当たる箇所は直さず報告する。未 commit の編集を上書きすると git に控えが無い。
5. 直しに関係する項目だけ確認し直す。直すと別の問題が生まれる。数値を消せば指示語が指す先を失い、短くすれば参照が空振りする。直しが lint / test / build の結果を変えうるなら、直しに関係する検証を通し直す。review の前の検証は、直す前の状態にしか当たらない。
6. 5 で新しい指摘が出たら手順 3 へ戻る。出なくなったら、commit できる状態かを判定して「出力」に従って返す。終わりを決めるのは、各観点の `確認` を通し切ったことだけ。「もう 1 巡回せば何か出る」は常に真なので、回数は根拠にならない。

## 観点

### スコープ

- 全ての変更行が依頼にトレースできるか。依頼のうち手を付けていないもの（TODO、仮実装、必要な検証を通していない箇所）が無いか。意図して外したなら、外したと言えるか。
- 性質の違う変更が 1 つに混ざっていれば、commit を分ける。
- 検証はここで実行しない。済んでいるかを確かめ、未実行なら review を止めて検証へ戻す。

確認: 変更行を 1 つずつ依頼に対応付け、依頼を 1 つずつ変更に対応付ける。対応先を言えない行と、手を付けていない依頼を挙げる。

### 事実

- 断定が観測を超えていないか。強い語（「できない」「必ず」「〜が原因」）だけでなく、`X の Y` を `X` へ、`〜の場合がある` を `〜する` へ広げる一段の拡張も見る。
- 同じことを書いた既存の doc と矛盾していないか。自分の書いた記録と食い違う説明は、何度読み返しても意図で読めてしまって気づけない。
- 推論を断定の形で書いていないか。実測値に測定時点と、何を数えた値かが付いているか。

確認: 断定を 1 つずつ根拠（ファイル、差分、コマンド結果、既存 doc）に当てる。当てられないものを挙げる。

### 整合性

- 参照が空振りしないか。1 つの概念に 1 つの語を使い、既存の表記に揃っているか。
- 変えた path、名前、設定キー、引用した文言、数えた値が、他の場所に古いまま残っていないか。本文を直すと、それを引用・要約している doc が黙って古くなる。

確認: 変えた語と数値を `rg` で検索する。参照は 1 つずつ辿る。

### 適用

書いたものを使う側の場面を再現する。読み返すだけでは出ない型がここで出る。

- 手順や規範なら、上から辿って各段の判定が決まるか。但し書きが、それを必要とする箇所から届く位置にあるか。
- 指摘を受けて直した箇所は、対応の範囲が指摘の趣旨を覆っているか。狭いと、同じ穴が別の入口に残る。

確認: 実際の依頼を 2〜3 想定して、書いたものを上から辿る。コードなら呼び出し側から見て成立するかを見る。

### 過剰さ

過剰さは、読み手が理解・判断するのに必要な水準を超えている部分。長さではなく、判断に効くかで見る。

- doc・文章: 同じ情報が 2 箇所以上に無いか（言い換え、節名と 1 文目、正本がある内容の写しを含む）。消しても読み手の判断が変わらない記述が無いか。同じ内容をより少ない量で言えないか。
- コード: 依頼されていない抽象、標準ライブラリ・platform の機能・既存の依存で足りる自前実装、消しても振る舞いが変わらないコードが無いか。security 境界の集約、security primitive の専用ライブラリ、多層防御、入力検証、fail-safe な default、timeout、失敗時の後始末は、これに当たらない。

確認: 重複は語と主張で検索する。判断に効くかは記述を 1 つずつ辿る。短くできるかは、周囲より突出して長い箇所を 1 度だけ言い換えて試す。より短い形は探せばいくらでも出るので、そこを追うと終わらない。

### doc

- 実装の変更に doc の追従が要るか。要否を黙って飛ばさない。
- notes が現在の設計を書いているか。変更履歴になっていないか。ADR の本文を書き換えていないか。

確認: 変更の種類ごとに、追従が要る doc 層（仕様 / ADR / notes）を挙げる。要らないなら要らないと言う。

## 独立 context を提案する条件

自己確認は自分が書いた文を見るのは得意だが、自分が調べた範囲の外は見えない。workspace 内の一次情報を取り直す目が要る場面では、下の条件ごとに書いた agent を提案する。複数の条件に当たれば、それぞれの agent を全部提案する。

- 実測や調査結果を根拠にした記述が多い。裏取りをやり直す価値がある。`quality-reviewer` を提案する。この agent は workspace で当て直せない出典しか根拠が無い主張を、当て直さずに返す。返ってきた主張は自分で確かめる。
- 契約、設定、skill / agent 定義など、間違うと影響が広い surface を触った。`quality-reviewer` を提案する。そのうち、権限や secret を持つ設定、実行される script（CI、build / install / setup script、hook）、agent が読む指示、追跡・配布・secret scanning の範囲を決める設定（`.gitignore`、配布対象の指定、secret scanner の除外設定）に触ったなら `security-reviewer` も提案する。
- auth、権限、secret、外部 I/O に触った。または、信頼境界の外（network、他の利用者、取得した file や tool の出力）から来る入力を、解釈・実行される先（command、path、query、HTML、deserialize、prompt など）へ渡す処理か、その検証や escape に触った。この skill は削って壊さないところまでを見るので、脆弱性そのものは拾えない。`security-reviewer` を提案する。
- 観点を通し切っても、直しが次の指摘を生む連鎖が止まらない。自分の盲点の可能性がある。`quality-reviewer` を提案する。

ユーザーが「じっくり」「独立で」と言った時、または agent 名を出した時は、提案を挟まず起動する。

## 扱わないもの

read と自分の変更の修正だけを行う。commit、push、履歴の書き換えは扱わない。bug の検出は `/code-review`、security は `/security-review`。doc の作成・更新は `scribe`。

## 出力

観点ごとに、`確認` で何をして何が無かったかを書く。「確認した」で済ませない。何を見たかが書けないなら、まだ見ていない。続けて、commit できる状態か、できないなら何が残っているか（未達 / 未検証 / ユーザー判断待ち）を書く。指摘が 1 件も出なかった場合も同じ 2 つを返す。

秘密情報にあたる値は報告へ転記しない。tracked file にも token、内部ホスト名、個人の絶対パスが混ざることがあり、報告に残すと秘密情報が履歴に残る。値ではなく、どのファイルのどの箇所かを書く。
