# coding skill の設計

- Date: 2026-09-03
- 出典: [Specification](https://agentskills.io/specification) / [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail) v4.9.0 / `dot_claude/skills/coding/` / この環境での実測

`coding` skill が今の形になっている理由を残す。skill 本体を読んでも分からない前提と判断に絞る。

## rule から skill へ移した理由

2026-09-02 まで、この内容は常時 load の rule に置いていた。移したのは、`paths` を使わない方針が決まった時に中身を数え直したため（[memory-surface-design.md](./memory-surface-design.md) の「rule でなく skill に置く基準」）。

見出しと空行を除くと実質 31 行あり、そのうち 20 行はコードを書く時だけ要るものだった。打ち切り順が 13 行で最大、可読性の具体が 4 行、コメントが 3 行。残る 11 行は品質の優先順位、適用の参照順、基本原則、最小差分で、設定や doc の編集にも効く。こちらは `CLAUDE.md` に残した。

旧 note は「コード限定は可読性の具体とコメントだけ」と書いていた。打ち切り順を数え落としている。最大の節が、コードを書く時にしか使われない。

分担は `CLAUDE.md` が「何が良いか」、この skill が「どう書くか」。境界は description に書いてある。`CLAUDE.md` は常時 load されるので、SKILL.md の本文で宣言し直す必要はない。

## 打ち切り順が品質の優先順位を上書きしない理由

打ち切り順は、コードを書く前にどの順で検討を打ち切るかを決める。原則を並べるだけでは、YAGNI と予防的抽象化の回避のどちらを先に当てるかが読み手ごとに変わる。順序を決めると、作らない判断が最初に来る。

節名に「停止」を使わない。打ち切り順と停止線はどちらも「実装前」と「止まる」を使うので、語が衝突する。意味は逆になる。停止線の「止まる」は実装せず人へ確認しろ、打ち切り順の「止まる」はその段で実装に入れ。「打ち切り順を通した」を「停止線を満たした」と読み替える余地を消したい。本文 1 行目には「止まる」が残っている。ただし目次と他所からの参照で使われるのは節名なので、取り違えはそちらから起きる。

7 段は ponytail のラダーを下敷きにしている。**段 6 だけ意図を変えて採った。** 原文の「一行にできるか → 一行にする」と "Shortest working diff wins" は、`CLAUDE.md` の「短さと巧妙さは目標にしない」を裏返す。ponytail 自身も `AGENTS.md` で "lazy means less code, not the flimsier algorithm" と補足しており、意図は近い。それでも文言のままだと優先順位が入れ替わって読める。採ったのは「同じ振る舞いで実装量が少ない形があるか」で、不変条件を振る舞い（境界条件と失敗時を含む）に置いた。可読性を落とす短縮も併せて禁じてある。短さは、その 2 つを満たした後に残る結果でしかない。

打ち切り順の直後に「品質の優先順位の上位を削る根拠にはならない」を置いた。この節だけを読むと、入力検証や security を「作らなくてよいもの」として扱う読み方ができるため。`CLAUDE.md` まで戻らせず、その場で閉じる。

段リスト冒頭の carve-out 参照、段 2 の再利用前の確認、段 4 の client 側の扱い、security primitive の段落、段 5 の停止線接続、bug fix 段落の境界文は、いずれも原文に無い追加。

段 2 と段 4 は、段が「成立した」と判定された瞬間に検討が止まる構造の穴を塞ぐ。典型は 2 つある。所有者検査の無い既存関数を段 2 で再利用する。`<input type="date">` を見て段 4 で日付検証を済ませたと判定する。段 4 は例の順序も DB 制約側へ寄せてある。

段 2 では、呼び出し元の権限まで見て判定する。耐えないと分かった後どうするかも書いた。入力と信頼境界だけで判定させると、誰が呼んだかの検査が入らない。`CLAUDE.md` 停止線の「認証認可、権限」とも語がずれる。行き先を書かないと段 3 へ降りる読みになり、弱い既存実装を残したまま検証経路が 2 つに増える。それは bug fix 段落が禁じている形だが、あちらは「bug fix は」で始まる。機能追加の途中で弱い helper を見つけた読み手には掛からない。

段 5 の停止線接続と bug fix 段落の境界文を置いたのは、打ち切り順が手続き的で直近の指示だから。「上から見て最初に成立した段で止まる」だけを辿ると、新しい依存の追加や共有関数の書き換えが確認を経ずに通る。停止線は `CLAUDE.md` にあって常時 load される。ただし打ち切り順の節は手順として自己完結して読めるので、参照へ戻る契機が無い。

「停止線」は段 2、段 5、security primitive の段落、bug fix 段落、コメント節の 5 箇所に出る。定義元の `CLAUDE.md` を書いたのは段 2 の初出だけ。5 箇所すべてに付けると、同じ修飾が 1 つの節に 4 回並ぶ。

## security primitive の carve-out を段リストの外に置いている理由

打ち切り順のどの段も、security primitive では逆向きに働く。通常のコードなら「既にあるものを使う」「標準ライブラリで足りる」「新しい依存を足さない」は security にプラスになる。security primitive では反転する。repo の自前 sanitizer を段 2 で再利用する。`Math.random()` を段 3 でトークン生成に使う。password hash を段 4 で DB の `SHA2()` に任せる。汎用 regex の依存を段 5 で sanitize に使う。段 5 に加えて `CLAUDE.md` の停止線も新しい依存の追加を止めるので、security 用ライブラリの採用だけ 2 段のハードルを越えることになるのも理由。

対象に SQL / shell / path の組み立てを入れたのは、injection の最大手が構築側にあるため。sanitize もパーサも解釈側を指す語なので、それだけだと文字列連結で query を組む経路が段 3 で成立して止まる。末尾に独自形式の行き先を書いたのは、用途向けのものも実績ある依存も無い形式で選択肢が尽きるのを避けるため。行き先の無い規範は迂回され、迂回が常態化すると carve-out 全体の効き目が落ちる。

carve-out への参照は段リストの冒頭に置いた。実装の供給源が 5 つあり、security primitive の流用はそのどれでも起きるため。段 2 が repo の既存実装、段 3 が標準ライブラリ、段 4 が platform のネイティブ機能、段 5 が既存の依存、段 7 が自前。段ごとに参照を張ると同じ文が 4 回並ぶ。段リストの後ろだけに置くと、どの段で止まった時点でも読まれない。なお段 5 が持つ停止線への接続は、依存を足す判断をした後に効く。既存の汎用依存で代用できると判定してその段で止まる経路は塞がない。

## bug fix の段落を打ち切り順と同じ節に置いている理由

打ち切り順の末尾に、bug fix を症状でなく root cause で直す段落を持つ。出典は ponytail の `skills/ponytail/SKILL.md`（"Bug fix = root cause, not symptom."）で、打ち切り順のラダーとは別立ての規範。

同じ節に置いたのは、2 つが同じ主張の裏表だから。ラダーは「作る量を減らす」。bug fix の段落は「呼び出し元ごとにガードを足すより、共有する側を 1 回直す方が差分が小さい」。どちらも実装量を減らす方向で、**根本原因を直すことと最小差分が対立しない**という点で繋がる。別の節に離すと、`CLAUDE.md` の「最小差分」だけを読んで症状パッチを選ぶ読み方が残る。

末尾に境界文を置いた。この段落は差分を小さくする指示であると同時に、影響範囲を広げる指示でもあるため。共有する側が公開インターフェースを持てば `CLAUDE.md` の停止線に当たる。呼び出し元を全部 grep した結果その大半が依頼と無関係なら、同じく `CLAUDE.md` の「作業中に別の問題へ気づいたら、その場で着手せずユーザーへ伝える」と「修正せず言及に留める」に当たる。段落だけを読んで「全部直す」へ倒れないよう、その場で確認へ繋いでいる。

## 命名と予防的抽象化を判断基準ベースにする理由

- **命名の汎用語リストに `handler` / `process` を入れない。** HTTP handler / event handler は framework が定義する確立した語で、`data` / `tmp` と同列に禁じると誤爆する。例外の根拠は「framework が定義する語である」に絞る。「近傍実装で使われている」を根拠にすると、「この repo は既に `helpers/` を使っている」でリスト全体を無効化できてしまう。
- **予防的抽象化の禁止列挙に `Provider` / `Manager` を入れず、例示に留める。** React の Provider や Nest / Spring の DI container は framework 規約が要求する構造で、自作の間接層とは別物。素の Node / Python で自作する DI container はこの規範が止めたい典型なので、例示は framework 名まで具体化する。
- `manager` が命名リストに残り `Manager` が抽象化リストから外れているのは整合する。命名 rule は識別子の曖昧さを見る。抽象化 rule は間接層の早期導入を見る。対象軸が違う。

## コメント marker を `tradeoff:` にしている理由

marker の書式は `SKILL.md` を正本とする。上限と作り直す条件の両方を書かせているのは、条件が無い marker が、後から読んだ人には放置と区別が付かないため。追跡は `rg -i 'tradeoff:'` の走査だけで、強制力は無い。

security に関わる上限を marker の対象から外した。`CLAUDE.md` の停止線が要求する人への確認を、コメント 1 行が代替する形になるため。`# tradeoff: token 比較は == のまま。timing attack が問題になったら constant-time へ` は、書式としては規約に完全に適合してしまう。marker の再構築条件は「〜が問題になったら」という事後トリガで、security ではその時点が侵害後を意味する。

語を `tradeoff:` にしたのは、コメント規約が既に「なぜ・制約・外部都合・トレードオフ」を挙げており、marker がその 4 番目の具体形になるため。ponytail の `ponytail:` をそのまま使うと、全 project へ配る成果物に外部プロダクト名が残る。ponytail を参照しなくなった後も語だけが残る。

**この規約は新規で、既存実態は 0 件。** 2026-09-01 時点、Markdown を除く tracked file を `rg` で見て marker は無い。この repo のコードは Neovim の Lua 設定が大半（tracked file の拡張子で Lua 28 / PowerShell 3 / zsh 2 / sh 2）なので、規約が効くのは主に配布先の project になる。

## 言語固有の形式を reference に分ける理由

charset、改行、BOM、必須の metadata、識別子の上限は言語ごとに違い、守らないとファイルが読み込めなくなる。可読性の判断より前に来る性質なので、SKILL.md 本体には言語共通の確認手順だけを置き、言語別は `references/` に分けている。公式が推奨する domain organization の形。

現在 reference があるのは VBA だけ。`.bas` / `.cls` は VBA 専用の拡張子ではない。`.cls` は LaTeX のクラスファイルと Salesforce Apex のクラス、`.bas` は FreeBASIC など他の BASIC 系でも使う。reference の冒頭に「拡張子だけで判断せず、Excel や Office の VBA だと確かめてから適用する」を置いた。2026-09-02 まで `paths` の `src/` 限定が果たしていた衝突抑止の代わり。

reference が無い言語のために、SKILL.md 側に確認すべき 3 点を一般則として書いてある。既存ファイルの charset / 改行 / BOM、識別子の上限と使える文字、toolchain が要求する metadata。VBA はその 1 例という位置づけで、言語が増えても SKILL.md を書き換えずに reference を足せる。
