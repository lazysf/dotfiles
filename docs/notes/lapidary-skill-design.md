# lapidary skill の設計

- Date: 2026-11-09
- 出典: [Extend Claude Code](https://code.claude.com/docs/en/features-overview) / [Extend Claude with skills](https://code.claude.com/docs/en/skills) / [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)（2026-11-08 確認） / [Best practices for skill creators](https://agentskills.io/skill-creation/best-practices) / [Specification](https://agentskills.io/specification) / [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail) v4.9.0 / 組み込みの `/code-review` と `/security-review` の instructions / この repo の review 運用の実測

`lapidary` skill が今の形になっている理由を残す。skill 本体を読んでも分からない前提と判断に絞る。

## skill に置く理由

commit 前の自己確認は、同じ観点の並びを毎回 chat へ書き下す形で運用していた。公式は「同じ playbook や多段手順を 3 回目に貼ったら skill にする」を目安に挙げている。CLAUDE.md 側の用途は「Project conventions, "always do X" rules」と説明され、例も `Use pnpm, not npm` の粒度。

CLAUDE.md へ観点を書かない理由は容量ではなく適用範囲にある。CLAUDE.md は全 session で常時 load される。review の時にしか要らない詳細を置くと、review しない session でも context を占める。いつ通すかも CLAUDE.md には置かず、`skills/git-commit` の手順が持つ（下の「`git-commit` に組み込まない理由」）。

ADR は書かない。3 条件のうち「覆すコストが高い」を満たさない（skill の追加は戻しやすく、公開 IF も永続化も持たない）。review の分担そのものを変える時は再検討する。

## `git-commit` に組み込まない理由

発火の起点が違う。この skill は commit の前と、「見直して」のような直接の依頼で走り、出力は commit できる状態かの判定になる。組み込むと、commit を伴わない「見直して」で review を通せない。

`git-commit` の責務も膨らむ。あちらは止まる条件、staging の規定、staged diff の確認を持つ。観点を本文に混ぜると、load されるたびに観点まで読むことになる。

`git-commit` の手順 4 が、commit する変更の全体をこの skill で見直す。発火の起点を足すだけで、観点は取り込んでいない。description だけに頼ると毎回は発火しなかった（数え方と結果は [git-commit-skill-design.md](./git-commit-skill-design.md) の「lapidary を手順で呼ぶ理由」）。

## commit の前に通す理由

commit の直前に通すのは、実装と doc をまとめて見直すため。失敗は両者を跨ぐ形で出る。設定を消したのに notes が古い参照を持ったまま。skill の `description` を変えたのに notes の記述が対応していない。分けて見直すと、実装だけを見る時点では doc がまだ無く、doc だけを見る時点では実装の差分を見ない。追従漏れを見つける場が消える。

commit は実装と doc で分けたままにする。見直しは変更セット全体を見る行為、commit は記録の粒度で、層が違う。

commit しない区切りでは通さない。その後の変更で結果が古くなる。区切りごとの確認は実装中の検証の役目。

## 目的を「仕上げる」に置いている理由

skill の目的は「変更を見直す」でなく「commit できる状態まで仕上げる」。見直すだけを名乗ると、指摘を挙げた時点で終われてしまい、未達が残ったまま次へ渡る。

「仕上げる」を目的にすると、見直すだけでは拾えない次の 3 点を持つことになる。

- 未達の検出。スコープ観点は、変更した行を依頼へ対応付ける（余分が無いか）のに加えて、依頼を変更へ対応付ける（手を付けていない依頼が無いか）。独立した観点を設けず、1 項目目を双方向にしてある。観点を増やすと 1 回が重くなるため（下の「観点を 4 つに絞っている理由」）。
- 検証の扱い。lint や test が通っているかを見る。
- 終わり方。出力は次の工程を挙げるだけでなく、commit できるかの判定にする。

目的の文は「指摘を並べることでも、拾ったものを全部直すことでもなく」と、直す量を目標にしないと書く。公式の [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices) は、「最後まで続けろ」と促す行は、止まるのを防ぐより over-work を招きやすいとしている。問題を探せと言われた reviewer は必ず何か見つけ、指摘を全部直すと余分な抽象や起こりえない場合の test が増える、とも書いている。何を直すかは手順 3 の当て直しで決まり、いつ終えるかは観点を通し切ったかで決まる。どちらも直した量では決まらない。

## 名前を `lapidary` にしている理由

目的が「commit できる状態まで仕上げる」なので、`review` を名前に置くと合わない。review は指摘を挙げる語で、挙げた時点で終われてしまう。

`lapidary` は宝石研磨師を指す。形容詞では「簡潔で彫琢された（文章）」の意を持つ。doc を主な対象にするこの skill と二重に噛み合う。`scribe`（写字生）と同じ職能名の型で揃う。

名前の正本はディレクトリ名。Claude Code の personal skill では frontmatter `name` が表示ラベルだけを決め、`/lapidary` はディレクトリ名から来る。一方 Agent Skills spec は `name` とディレクトリ名の一致を必須にしているため、両方を揃えてある。

名前は中身を説明しない。`self-review` のような名前なら、「自分の変更を自分で見る」ことを名前が説明できる。`lapidary` は説明しないので、description の冒頭「自分が加えた変更を」が説明を担う。

## 自動で発火させる理由

明示指定だけにすると、人が呼ばない限り見直しの工程が通らない。2026-09-03、description を明示指定へ絞った状態でこの skill 自身と関連 notes を変更する作業を回したところ、一度も発火しなかった。lint と参照検索が手で行われ、観点が通らないまま commit の手前まで進んだ。

実装（`coding`）と doc（`scribe`）は自動で発火する。見直しだけが人の呼び出しに依存すると、`scribe` が書いた doc の仕上げが走らないまま commit へ進む。

`disable-model-invocation: true` は採らない。`/lapidary` と打った時しか走らず、明示指定と変わらないため。

入口の実行条件は置いていない。この skill は作業ツリー内で閉じ、履歴も外部も触らない。代わりに手順 4 が、直す対象を自分の変更と、それが古くした記述に限っている。元からあった問題とユーザー自身の編集は直さない。`git-commit` が「ユーザー自身が編集した変更は unstaged に残す」を持つのと対になる。一般則は [harness-design-principles.md](./harness-design-principles.md) の「発火面と実行条件を分ける」にある。

## 検証を実行せず確認だけする理由

lint、test、build は、実装の途中で回す検証の役目で、見直しの前に済んでいる。skill 側で実行すると二重になる。未実行なら見直しを止めて検証へ戻す。

手順 4 の直しが lint、test、build の結果を変えうるなら、手順 5 で通し直す。見直しの前の検証は直す前の状態のもので、直した分は未検証のまま commit へ進みうる。発火が commit の前に限られ、見直しの後に区切りが無いので、この穴は表に出やすい。

## 観点を 4 つに絞っている理由

公式は「網羅しすぎた skill は、関係ない指示に引きずられて不要な経路を辿る」ため、簡潔で段階的な手順を勧めている。観点を増やすほど 1 回が重くなる。

4 つ（スコープ、事実、整合、過剰さ）は、この repo で実際に指摘として出たものから採った。

手順を縛らないことと、終わりを決めないことは別だった。観点だけを挙げて何を確かめるかを書かずにいた間は、読む角度が回ごとに変わり、新しい角度からは必ず新しい指摘が出る状態になっていた。各観点の項目が「何を何に当てるか」まで書いているのはそのため。何をすれば通したことになるかを決めると、角度はその側で決まる。

項目の文言は、実際に出た指摘の型から作っている。「事実」が一段の拡張（`X の Y` を `X` に広げる）を名指しするのは、「観測を超えていないか」という抽象だけでは自分の書いた文に効かなかったため。根拠に「既存の doc」を含めるのは、自分が notes に書いた記録と矛盾する説明を、読み返しても意図で読めてしまって見逃した実例による。「整合」が path や設定キーだけでなく引用した文言と数えた値まで見るのも、本文を直して notes 側が黙って古くなる型が繰り返し出たため。

## 「過剰さ」の定義

今の定義（正本は `dot_claude/skills/lapidary/SKILL.md`）は「読み手が理解や判断に使わない部分」。絶対評価ではなく、目的に対する相対評価にしてある。

「消しても主張が変わらない記述がないか」という定義は判定が主観で、何度読んでも「これも消せる」が出た。青天井の観点が 1 つあると全体が終わらない。

捨てた定義も書いておく。一度「読む量が増えるのに、読み手が得る情報が増えない箇所」という絶対評価の定義を採り、却下した。これだと情報が増えない箇所（重複、空の指示語）しか拾えない。情報は増えるが判断には不要な記述が漏れる。正しいが使われない詳細、同じ内容の迂遠な言い回しがそれに当たる。次に定義を触る時、同じ狭め方を繰り返さないために残す。

## 「過剰さ」を doc とコードで分けている理由

観点のうち「過剰さ」だけが、対象が doc かコードかで分岐している。読み手の判断に効かない記述と、頼まれていない抽象は、どちらも過剰だが探し方が違う。前者は書いた文を字面で読み直せば出るのに対し、後者は呼び出し元を数えないと出ない。

コード側に除外を添えてあるのは、過剰さの特徴と security の正しい形が重なるため。auth middleware や sanitize wrapper のように境界を 1 箇所へ集約した層は、呼び出し元が 1 つであることが正しい。多層防御（timeout、`finally` の後始末、fail-safe な default、境界を越えた後の再検証）は、定義上、正常系で振る舞いが変わらない。効くのは異常系と敵対的入力だけ。除外が無いと、この観点がそれらを毎回の削除候補として名指しする。この skill は commit 前の既定の工程で回り、security の review はユーザーが選んだ時だけ走るので、削る側だけが既定で動くことになる。

## 指摘そのものを当て直す理由

観点は不揃いと欠落を検出する。検出したことと、直す価値があることは別。後者を判定しないと、検出がそのまま報告へ流れる。

2026-09-07 に実例が出た。「事実」観点の「実測値に、いつ何を数えた値かが付いているか」に当てて、`docs/notes/lint-and-pre-commit-execution.md` の実測 1 件に日付が無いことを検出した。これを「範囲外で 1 件」として報告へ載せた。ユーザーが対応の要否を聞き返した時点で段落を読み直すと、最終文が見直しの入口を持っていた。日付を足しても誰の判断も変わらない。

そのため手順 3 で、拾ったものごとに「直さないと、誰のどの判断や動作が変わるか」を 1 文で言えるかに当てる。観点を増やさず手順へ置いたのは、観点は変更を見るもので、この判定は自分が出した指摘を見るものだから。対象が違う。

## 直す範囲を、自分の変更と、それが古くした記述にしている理由

「整合」の観点は、変えた path や文言を引用・要約している場所を探す。そこで見つかる追従漏れは、自分の変更が原因で古くなった記述で、多くは自分がまだ触っていないファイルにある。直す範囲を「自分が加えた変更」だけにすると、見つけた追従漏れを直せず、報告に回すしかない。2026-11-09 に、Codex が `dot_codex/` の skill を直した時、それを説明する notes が古いまま残ることを報告に挙げ、直さずに commit した。規則のとおりの動きだった。

元からあった問題は、今も直さずに報告する。判定は、原因が自分の変更にあるかで決める。範囲外のファイルにあっても、自分の変更が古くしたなら直す。自分の変更が無くても古かったなら、触らない。契約の「作業中に見つけた無関係の問題は、直さずにユーザーへ伝える」とも食い違わない。追従は、自分の変更と関係がある。

追従した notes は、repo の `AGENTS.md` のとおり surface の変更とは別の commit にする。見直しは変更セット全体を見る行為で、commit の分け方とは層が違う（上の「commit の前に通す理由」）。

## 組み込みの review を提案に留める理由

この skill は agent を起動しない。独立した context の review は、組み込みの `/simplify`、`/code-review`、`/security-review` を提案するだけにしている。自作の reviewer agent は、必要になってから作る。

組み込みの review と自己確認は、拾うものが違う。`/code-review` の instructions は correctness bug を探すよう指定する。反転した条件、off-by-one、null 参照、await 漏れ、外れた guard、壊れた caller、race。そのうえで "Prefer real failure modes over style" と、style 系の指摘を明示的に下げる。この skill が見る scope の逸脱、実体の二重管理、参照の追従漏れはこの範囲に入らない。当時の reviewer agent の定義と `CLAUDE.md` の diff を `/code-review` へ通したところ、findings は 0 件だった。そのため自己確認を既定の工程にし、組み込みの review は正しさと security の目が要る変更でだけ提案する。

走らせるかはユーザーが決める。ユーザーが「じっくり見て」と言った時だけ、提案を挟まずに走らせる。

`/security-review` は commit の後、push の前に置く。`/security-review` は origin の default branch との差分のうち、commit 済みのものだけを見る（子 session で実測）。commit の前に走らせても何も見ない。

## 出力に秘密情報の値を写さない理由

この skill は security の検出を持たない。脆弱性を見つけるのは `/security-review` の側。

それでも出力の規定を置くのは、値を報告へ写す経路が構造として在るため。毎回 diff 全体を読み、観点ごとに何を見たかを出力する。sandbox の deny は `.env` などの read を止めるが、tracked file 内の値は止めない。自分の出力に対する規律であって、値を探す仕事は増やしていない。

`git-commit` の同種の規定と文言を揃えていないのは、露出する経路が違うため。あちらは `git` の command 出力に認証 URL や token が混ざる形で、こちらは読んだ file の中身を写す形になる。

## 過剰設計の review を別 skill にしていない理由

公式は skill の粒度を関数と同じように考えるよう勧めている。狭すぎる skill は 1 つのタスクに複数 load され、overhead と指示衝突を招く（Best practices の "Design coherent units"）。過剰設計だけを見る skill を独立させると、変更を閉じる時に `lapidary` と 2 本呼ぶ運用になり、スコープと整合の観点は両方に必要なので重複する。

ponytail の `ponytail-review` が持つ tag 形式（`delete:` / `stdlib:` / `native:` / `yagni:` / `shrink:` と `net: -N lines possible.`）も採っていない。この skill の出力は「観点ごとに何を確かめたか」で既に決まっており、tag と行数集計を足すと、同じ指摘に 2 つの書式が並ぶ。

repo 全体を対象にした bloat の洗い出し（ponytail の `ponytail-audit` に当たる）は持たない。この skill は自分が加えた変更を見る入口で、repo 全体の走査は別の作業になる。

## 終わりを回数でなく網羅で決めている理由

終わりを決めるのは、4 つの観点を通し切ったことだけ。回数では決めない。

「2 巡続けて指摘 0」で閉じる形は機能しなかった。2 巡 0 で閉じた変更に対して `/lapidary` を明示で 3 回呼び直したところ、9 件・7 件・7 件が出た（2026-09-01）。出たものには事実の誤りと、rule として機能しない箇所（段の判定が決まらない、参照が必要な段に届かない）が含まれていて、推敲の水掛け論ではない。

原因は 2 つ。観点に終わりの無いものが混ざっていた。当時の「過剰さ」の定義「消しても主張が変わらない記述がないか」は判定が主観なので、厳密に適用すれば常に何か見つかる。もう 1 つは読む角度が未定義だったこと（上の「観点を 4 つに絞っている理由」）。「もう 1 周すれば何か出る」は常に真になり、収束の判断に使えない。公式も、結果が回ごとにぶれる原因の 1 つとして「指示が曖昧でモデルが毎回違う解釈をする」を挙げている。

直すと別の問題が生まれる、という観察自体は正しい。だから手順 5 に「直した箇所に関係する観点だけ確かめ直す」を置いてある。全部やり直さないのは、通し切った観点をもう一度通しても、直しが触っていない箇所からは新しいものが出ないため。

## 未確認

- 自己確認が拾えない型を、今の構成で拾えるか。当時の reviewer agent が拾った 4 つ（`git log` の committer date が示す履歴書き換え、schema の実 default、観測を超えた一般化、スコープ外の混入）は、どれも一次情報を取り直さないと出ない。組み込みの review がこれらを拾うかは試していない。
- 秘密情報の値の転記が実際に起きたかは確認していない。出力の規定は、経路が在ることに対して置いた。
- commit しない区切りで発火しないかは、観測していない。`git-commit` の手順 4 から通す形が毎回効くかは未測定。公式が model behavior を nondeterministic と明記しているため、1 回の発火では判定できない。
