# Coding Standards

全言語に共通する実装の基本原則。

- 判断の優先順位は、リポジトリの明示規約 → 近傍実装の書き方 → 依頼を満たす最小差分 → 基本原則の順。
- 基本原則は `可読性優先`、`KISS`、`YAGNI`、`DRY` の順で重みづけし、上位を損なう下位適用はしない。

## 基本原則

### 可読性優先

- 読み手が意図、責務、流れを追いやすい形を優先する。
- 行数目標のためだけに関数分割しない。
- コメントは、見れば分かる処理ではなく、制約や意図がないと読み取りにくい箇所にだけ置く。

### KISS

- 目的を満たす単純で検証しやすい案を選ぶ。
- 初回実装は最小で直線的なコードを優先し、動作確認後に必要な整理だけ行う。
- 失敗しうる境界では、何が失敗したか後から追える形を残す。

### YAGNI

- 未確定の将来要件を先回りして組み込まない。
- module 分割、class 化、interface 化、helper 化、設定化、新規依存追加は、重複・責務肥大・検証困難などの実害が確認できるまで遅らせる。
- 内部処理で必要以上の防御コードや設定層を増やさない。理由の薄いラッパーや helper を足さない。

### DRY

- 重複は、実害や保守負荷があり、単純さを損なわない場合だけ解消する。
- 抽出や共通化で分岐、引数、概念名、読み先が増えるなら、その時点では重複を残してよい。
- 同じ形でも、意味や変更理由が違う処理は共通化しない。
- 可読性と保守性が明確に改善する場合だけ共通化する。
