# Coding

`rules/quality.md` が「何が良いコードか」を持ち、この skill は「どう書くか」を持つ。優先順位、参照順、基本原則、最小差分はあちらが正本で、ここでは扱わない。

## 実装前の打ち切り順

コードを書く前に上から見て、最初に成立した段で止まる。security primitive が要る時は、どの段で止まっても下の security primitive の段落に従う。

1. **作る必要があるか**: 未確定の将来要件なら作らない。
2. **このコードベースに既にあるか**: helper、util、型、既存パターンがあれば再利用する。記憶で判断せず検索する。再利用する前に、その実装が今の入力、呼び出し元の権限、信頼境界に耐えるか確認する。耐えないなら、直すか使わないかを `CLAUDE.md` の停止線に従って確認する。
3. **標準ライブラリで足りるか**: 足りるなら使う。
4. **platform のネイティブ機能で足りるか**: DB の制約、CSS、`<input type="date">` など。ただし client 側の機能は表示と入力補助であって、信頼境界を越える入力の検証には数えない。
5. **既存の依存で解けるか**: 解けるなら新しい依存を足さない。解けずに足すなら、停止線に従って確認する。
6. **同じ振る舞いで実装量が少ない形があるか**: 境界条件と失敗時を含めて振る舞いが同じなら、実装量が少ない方を取る。読みにくくなる短縮は取らない。
7. **ここで初めて**: 依頼を満たす最小の実装を書く。

段を降りるのは問題を理解した後。何を触るか分からないまま小さく直すのは、最小差分ではなく 2 つ目の bug。

**この打ち切り順は実装量を減らす手順で、`rules/quality.md` の「品質の優先順位」の上位を削る根拠にはならない。** 入力検証、失敗時のデータ保全、security、accessibility、明示的に依頼されたものは、どの段でも落とさない。選択肢が複数あるなら、実装量に関わらず境界条件で正しい方を取る。

security primitive は自前実装せず、その用途向けに設計されたものを使う。対象は暗号、認証、sanitize、信頼できない入力を解釈するパーサ、SQL / shell / path の組み立て（parameterized query、専用の escape API、path canonicalization）。repo の既存実装、標準ライブラリ、platform のネイティブ機能、既存の依存のどれにあっても、汎用機能で代用しない（乱数は暗号用の API、password は専用の hash、sanitize は専用ライブラリ）。

用途向けのものが無ければ、実績のある依存の追加を停止線に従って確認する。独自形式で該当する依存も無いなら、入力サイズと再帰の上限、失敗時の拒否を決めてから書く。

bug fix は症状でなく root cause を直す。触る関数の呼び出し元を全て検索し、共有する側を一度直す。呼び出し元ごとにガードを足すより差分が小さく、報告された経路だけ直すと兄弟の呼び出し元が壊れたまま残る。ただし共有する側が公開インターフェースを持つ場合、または呼び出し元の大半が依頼と無関係な場合は、直す前に停止線に従って確認する。

## 可読性の具体

- **直線化**: 正常系を上から下へ読める形にする。異常系はガード節で早期 return して直線を保つ。
- **命名**: ドメインの意味を表す。`data` / `tmp` / `result` / `manager` / `helper` / `util` のような中身を説明しない語は、極小スコープで意味が自明な時だけ。framework が定義する語（HTTP handler、event handler 等）はこれに当たらない。
- **副作用の分離**: 純粋な計算・バリデーションと、DB / API / ファイル I/O / ログ / 通知を混ぜない。
- **予防的抽象化を避ける**: 間接層（Factory / Strategy / BaseClass、helper、設定層 等）は、今の変更圧力が出てから入れる。framework の規約が要求する構造（React の Provider、Nest / Spring の DI container 等）はこれに当たらない。

## コメント

- 「なぜ・制約・外部都合・トレードオフ」を書く。「何をしているか」のコード言い換えは書かない。
- 意図的に簡略化して既知の上限を残した箇所は `tradeoff:` で始め、上限と作り直す条件を書く。条件が無いと、後から読んだ人が今も妥当か判断できない。例: `# tradeoff: 全体 lock。throughput が問題になったら口座ごとの lock へ`
- security に関わる上限は `tradeoff:` で閉じない。停止線に当たるので、コメントに残さずユーザーへ確認する。

## 言語固有の形式と制約

言語や toolchain には、守らないとファイルが読み込めなくなる形式がある。charset、改行、BOM、必須の metadata、識別子の上限などで、これらは可読性の判断より前に来る。壊れたファイルは可読性以前に動かない。

書く前に確認する。

- 既存ファイルの charset / 改行 / BOM。**明確な既存形式があれば、既定より既存を優先する。** 一貫性が崩れると diff がファイル全体に広がる。
- 識別子の上限と使える文字。言語仕様で確かめる。記憶で書くと、長い名前がコンパイル時まで気づかれない。
- toolchain が要求する metadata。import や build が読む行で、消すとファイルの identity が失われる。

該当する言語の reference があれば読む。

- VBA（`.bas` / `.cls`）: [references/vba.md](references/vba.md)

reference が無い言語は、上の 3 点を言語仕様で確認してから書く。
