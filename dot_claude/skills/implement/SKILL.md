# 実装ループ

テスト可能な変更を、確認方法先行の小さなループで進める。

## 基本方針

- 先にテスト、再現手順、比較観点のいずれかを置く。
- `tasks.md`、`detailed-design.md`、`requirements.md` に沿って実装する。
- 最小差分で進め、次の差分を増やしすぎない。
- 近傍実装と明示規約に寄せて、いま必要な振る舞いだけを満たす。
- 要件変更や設計変更を勝手に行わない。必要なら lead に戻す。
- 未検証事項は成功扱いにしない。
- 実装結果は `implementation.md` に記録する。

## 手順

- 対象 `TASK-*` / `DD-*` / `AC-*` を確認する。
- 変更前に確認方法を置く。
- 最初は対象 task を満たす最小で直線的な差分に留める。
- 既存 pattern、命名、責務、エラー処理、テスト配置に寄せる。実装、テスト、スクリプトの基本原則は [coding-standards rule](../../rules/coding-standards.md) を正本とする。
- 抽象化、分割、helper 化、新規依存追加が必要に見える場合は、理由、影響範囲、より単純な代替案を先に確認する。
- コメントは、見れば分かる処理ではなく、制約や意図がないと読み取りにくい箇所にだけ置く。
- 失敗しうる境界では、何が失敗したか後から追える形を残す。
- 追加した確認を再実行し、結果と未確認事項を分ける。
- 動作確認後、読みやすさ、変更容易性、検証容易性が明確に改善する整理だけ行う。
- 実装中に上流問題が見つかった場合は、要件や設計を書き換えず lead に返す。

## 代替確認

テストを先に書きにくい変更では、確認手段を明示してから進める。

- docs-only 変更: 記述先と現行実装、既存導線との整合確認。
- 設定変更: 影響する設定キー、既定値、読み取り箇所、回帰の確認。
- 小さなスクリプトや運用変更: 実行条件、入力、期待結果の確認。
- UI や出力整形: 再現手順、比較観点、差分確認。

確認したことと未確認事項を分けて残す。

## 境界

- 原因調査は `research`。
- 要件整理や技術計画は `grill`。
- 実装計画の合意形成は `grill`。合意済みの計画や docs の記録・整形は `scribe`。
- Excel VBA の exported `.bas` / `.cls` を作成・編集する時は、その環境固有の注意点を [references/vba-best-practices.md](references/vba-best-practices.md) に置いているため、書く前に読む。

## 完了条件

- 対象 `TASK-*` に対応する変更がある。
- 変更意図に対応する確認方法がある。
- 実装後に確認が通っている、または未実行理由と残リスクが明示されている。
- `implementation.md` に対応 task、変更内容、変更ファイル、未確認事項が記録されている。
