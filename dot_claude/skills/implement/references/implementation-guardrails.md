# 実装ガードレール

実装ループで迷う判断を、既存コンテキスト優先でそろえる。

## 基本原則

4 原則の優先順位は、`可読性優先`、`KISS`、`YAGNI`、`DRY` の順とする。
DRY は有効だが、上位原則を損なう共通化はしない。

### 可読性優先

- 名前、責務、構造、コメントは、読み手が意図を追いやすいことを優先する
- 命名、責務の切り方、エラー処理、テスト配置は近傍実装に寄せる
- コメントは、見れば分かる処理ではなく、制約や意図がないと読み取りにくい箇所にだけ置く
- 行数目標のためだけに関数分割しない

### KISS

- 依頼を満たす、理解しやすく検証しやすい最小案から始める
- 初回実装は、最小で直線的なコードを優先し、動作確認後に必要な整理だけ行う
- 近傍実装と明示規約に沿う素直な実装を既定にする
- 外部入力、公開面、永続化、権限、秘密情報などの境界を優先して堅くする

### YAGNI

- 将来前提の抽象化、設定、拡張ポイントを追加しない
- module 分割、class 化、interface 化、helper 化、新規依存追加は、既存パターンまたは重複・責務肥大・検証困難などの実害が確認できるまで遅らせる
- 内部処理では、必要以上の防御コードや設定層を増やしすぎない
- 理由の薄いラッパーや helper を増やさない
- 依頼範囲外の広域リネームや横展開を混ぜない

### DRY

- 実害のある重複だけを解消し、将来のためだけの共通化はしない
- 抽出や共通化で分岐、引数、概念名、読み先が増えるなら、その時点では重複を残してよい
- 可読性と保守性が明確に改善する場合だけ共通化する

## 優先順位

1. リポジトリの明示規約
2. 近傍実装の書き方
3. 今回の依頼を満たす最小差分
4. 4 原則の優先順位

## 実装時のガードレール

- まず最小で直線的な実装を作り、確認後に必要な場合だけ整理する。
- 抽象化や分割が必要に見える場合は、理由、影響範囲、より単純な代替案を確認してから進める。
- 外部入力、公開面、永続化、権限、秘密情報などの境界を優先して堅くする。
- 失敗しうる境界では、何が失敗したか追える形を残す。
- 実行できた確認と未検証事項を分ける。

## 避けること

- 将来前提の抽象化や拡張ポイントの追加
- 初回からの大きな module 分割、class 化、interface 化、設定化
- 理由の薄いラッパーや helper の増殖
- 依頼範囲外の広域リネームや横展開
- 未検証事項を成功扱いすること

## 注意点

- 同じ形でも、意味や変更理由が違う処理は共通化しない
- helper 化で呼び出し側が読みにくくなるなら、その helper は作らない
- 将来の拡張可能性だけを理由に抽象化しない

## 仕上げ前の確認

- 今回の依頼を満たす最小差分に留まっている
- 近傍実装と明示規約に沿った書き方になっている
- 共通化によって分岐、引数、概念名、読み先が不要に増えていない
- 境界の入力、失敗時の扱い、既存契約の破壊有無を確認した
- 実行できた確認と未検証事項を説明できる
