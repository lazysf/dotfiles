# Lapidary

変更を commit できる状態まで仕上げる。観点を通し、見つけた不足と過剰を直し切ってから次へ渡す。**目的は指摘を挙げることではなく、仕上げ切ること。**

## 手順

1. `git status -sb` と `git diff`（staged があれば `git diff --staged` も）で変更の全体を読む。
2. 観点 6 つを全部通す。各観点の `確認` に書かれたことをやり、何を確認して何が無かったかを持つ。
3. 見つけた指摘を直す。**直す対象は自分が加えた変更に限る。** ユーザー自身が編集した箇所と、`CLAUDE.md` の停止線に当たる箇所は直さず報告する。未 commit の編集を上書きすると git に控えが無い。直したら、その直しに関係する項目だけ再確認する。全部やり直さない。
4. 3 で新しい指摘が出なくなったら、commit できる状態かを判定して「出力」に従って返す。

**直すと別の問題が生まれる。** 数値を消せば指示語が指す先を失い、記述を強めれば根拠を超え、短くすれば参照が空振りする。最初に見た時には無かった問題が、直した後に現れる。手順 3 はそのためにある。

**回数は収束の根拠にならない。** 「もう 1 巡回せば何か出る」は常に真。終わりを決めるのは、各観点の `確認` を通し切ったことだけ。

## 観点

### スコープ

- 全ての変更行が依頼にトレースできるか。ついで改善や無関係な整形が混ざっていないか。
- 依頼のうち手を付けていないものが無いか。TODO、仮実装、必要な検証を通していない箇所を残していないか。意図して外したなら、外したと言えるか。
- 性質の違う変更が 1 つに混ざっていないか。混ざっていれば commit を分ける。

**検証はここで実行しない。** lint / test / build が済んでいるかを確認するだけ。工程表では検証が review の前の別工程なので、ここで実行すると二重になる。未実行なら review を止めて検証へ戻す。

確認: 変更行を 1 つずつ依頼に対応付け、依頼を 1 つずつ変更に対応付ける。対応先を言えない行と、手を付けていない依頼を挙げる。

### 事実

- 断定が観測を超えていないか。「できない」「必ず」「〜が原因」のような強い語だけでなく、`X の Y` を `X` へ、`〜の場合がある` を `〜する` へ広げる一段の拡張も、確かめていない範囲を含む。**同じことを書いた既存の doc があるなら、そちらと矛盾していないか照らす。** 自分の書いた記録と食い違う説明は、何度読み返しても意図で読めてしまって気づけない。
- 推論を断定の形で書いていないか。推論なら推論と分かる形か。
- 数値と日付が今も成り立つか。実測値に測定時点と、何を数えた値かが付いているか。範囲を書かない数値は、後から別の範囲で数え直されて食い違う。

確認: 断定を 1 つずつ根拠（ファイル、差分、コマンド結果、既存 doc）に当てる。当てられないものを挙げる。

### 整合性

- 参照が空振りしないか。リンク先に、期待させた内容があるか。
- 1 つの概念に 1 つの語を使っているか。既存の表記に揃っているか。
- 変えた path、名前、設定キー、引用した文言、数えた値が、他の場所に古いまま残っていないか。本文を直すと、それを引用・要約している doc が黙って古くなる。

確認: 変えた語と数値を `rg` で検索する。参照は 1 つずつ辿る。

### 適用

書いたものを使う側の場面を再現する。読み返すだけでは出ない型がここで出る。

- 手順や規範なら、上から辿って各段の判定が決まるか。「どちらとも読める」段が無いか。
- 参照や例外が、それを必要とする箇所から届く位置にあるか。後ろに置いた但し書きは、途中で止まった読み手に読まれない。
- 指摘を受けて直した箇所は、対応の範囲が指摘の趣旨を覆っているか。狭いと、同じ穴が別の入口に残る。

確認: 実際の依頼を 2〜3 想定して、書いたものを上から辿る。コードなら呼び出し側から見て成立するかを見る。

### 過剰さ

**過剰さは「読み手が理解・判断するのに必要な水準を超えている部分」。** 情報が有るか無いかではなく、目的に対して多すぎるかで見る。判断に効かない情報は、正しくても過剰。長さそのものは問題ではない。判断に効くなら長くてよい。

doc・文章の変更:

- 同じ情報が 2 箇所以上に無いか。同じ主張、同じ列挙、節名と 1 文目、正本がある内容の写し。言い換えて 2 回言うのも含む。
- 消しても読み手の判断が変わらない記述が無いか。「これは誰のどの判断に効くか」に答えられないものは落とす。指す先を持たない指示語や、根拠を持たない修飾はその極端な場合。
- 同じ内容をより少ない量で言えないか。1 文で足りることを複数文で書いていないか。

コードの変更:

- 依頼されていない抽象を足していないか。単一実装の interface、1 つしか作らない factory、変わらない値の設定、呼び出し元が 1 つの層。auth や sanitize のように security 境界を 1 箇所へ集約したものと、許可 origin 一覧のような security 上の固定値はこれに当たらない。
- 標準ライブラリ、platform のネイティブ機能、既存の依存で足りるものを自前で書いていないか。既にある helper や pattern の再実装になっていないか。逆に、それらで足りるのに新しい依存を足していないか。security primitive の専用ライブラリは、汎用機能で代用できるように見えてもこれに当たらない。
- 消しても振る舞いが変わらないコードがないか。多層防御、入力検証、fail-safe な default、timeout、監査ログ、失敗時の後始末は、正常系で変わらなくても消さない。

確認: 重複は語と主張で検索する。判断に効くかは記述を 1 つずつ辿る。短くできるかは、周囲より突出して長い箇所を **1 度だけ**言い換えて試す。より短い形は探せばいくらでも出るので、そこを追うと終わらない。

### doc

- 実装の変更に doc の追従が要るか。要否を黙って飛ばさない。
- notes が現在の設計を書いているか。変更履歴になっていないか。
- ADR の本文を書き換えていないか。

確認: 変更の種類ごとに、追従が要る doc 層（仕様 / ADR / notes）を挙げる。要らないなら要らないと言う。

## 独立 context を提案する条件

自己確認は自分が書いた文を見るのは得意だが、自分が調べた範囲の外は見えない。一次情報を取り直す目が要る場面では `quality-reviewer` / `security-reviewer` agent を提案する。

- 実測や調査結果を根拠にした記述が多い。裏取りをやり直す価値がある。
- 契約、設定、skill / agent 定義など、間違うと影響が広い surface を触った。
- auth、権限、secret、外部 I/O に触った。この skill は削って壊さないところまでを見るので、脆弱性そのものは拾えない。
- 観点を通し切っても、直しが次の指摘を生む連鎖が止まらない。自分の盲点の可能性がある。

ユーザーが「じっくり」「独立で」と言った時、または agent 名を出した時は、提案を挟まず起動する。

## 扱わないもの

read と自分の変更の修正だけを行う。commit、push、履歴の書き換えは扱わない。bug の検出は `/code-review`、security は `/security-review`。doc の作成・更新は `scribe`。

## 出力

観点ごとに、`確認` で何をして何が無かったかを書く。「確認した」で済ませない。何を見たかが書けないなら、まだ見ていない。続けて、commit できる状態か、できないなら何が残っているか（未達 / 未検証 / ユーザー判断待ち）を書く。指摘が 1 件も出なかった場合も同じ 2 つを返す。
