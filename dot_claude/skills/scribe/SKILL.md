# Scribe

repo が独自の doc 規約（置き場、形式、作る時期）を持っていれば、そちらに従う。この skill は、規約が無い部分の既定。

## 3 層の使い分け

| 層 | 中身 | 置き場 |
| --- | --- | --- |
| 仕様・使い方 | 何を・どう使うか | `README.md` / `docs/` |
| ADR | なぜそうしたか（比較した判断） | `docs/adr/` |
| notes | 背景、調査、今の設計の理由 | `docs/notes/` |

ADR と notes は、確かめた事実から作る。判断や調査の結果が出る前に書かない。

## notes は今の設計を書く

notes に変更履歴を書かない。「旧規定は〜だった」「〜に直した」ではなく、「今こうなっている。理由は〜」と書く。なぜ変えたかは commit の `Why:` が持つ（git-commit の規定）。

例外は、同じ失敗を繰り返さないために要る事実。「この設定を入れると別の機構が壊れる」「この方法は試して効かなかった」は、今の設計の理由として書く。

複数案を比べた判断は ADR に書く。ADR の 3 条件を満たさない判断は notes でよいが、その場合も「なぜ今この形か」として書き、検討の経緯を並べない。

## ADR を作る条件

3 つ全部を満たす時だけ作る。

1. **複数案を実際に比べた**: 仮想ではなく、実在する代替案を検討した。
2. **覆すコストが高い**: 公開 IF、データ形式、永続化、認証、依存に関わり、後で方向を変えると痛い。
3. **捨てた案に再検討の価値がある**: 後の読み手が「なぜ A でなく B か」を疑問に思う。

戻しやすい判断、明らかな判断、実質的な代替案が無い判断では作らない。3 条件を満たさないのに ADR を求められたら、不要と明示するか notes を提案する。

## 既存 ADR の扱い

本文は採用時点の記録として残す。方針の変更、判断の補正、理由の再解釈は、本文を書き換えず新しい ADR に書く。

直接編集してよいのは次の 2 つだけ。

- `Status`、`Superseded-By`、`Amended-By` などの状態と関係のメタデータ
- typo、リンク切れ、Markdown の破損など、判断の内容を変えない修正

関係のメタデータ（`Supersedes` など）は推測で書かない。ユーザーの依頼か会話上の合意で確かめられたものだけ使う。

## 進め方

- 既存の自然な位置に差し込む。新しい doc は、既存に収まらない時だけ作る。
- 既存の章構成、用語、粒度、文体に寄せる。1 つの概念に 1 つの語を使い、途中で言い換えない。
- doc を追加・削除・rename したら、README、索引、相対リンクの追従を確かめる。直せないリンク切れは、場所と理由を残す。
- 書く前に、対象の reference を 1 つだけ読む。記憶で書かない。
  - README / docs: [references/readme-format.md](references/readme-format.md)
  - ADR: [references/adr-format.md](references/adr-format.md)
  - notes: [references/notes-format.md](references/notes-format.md)

## 文体と分量

- 1 文に 1 つの主張。2 つ以上の主張を「〜し」「〜で」「〜が」で繋がない。
- 修飾を浅く保つ。名詞を助詞なしで連ね続けない。連体修飾を入れ子にしない。
- 造語の名詞化を避ける。「判定語」「受け皿」のような名詞を作らず、動詞で書く。
- 略語を作らない。DB、API、URL のような定着した語だけ使う。
- 断定できることは断定する。確度が低い時だけ、その理由と一緒に示す。
- 書くかどうかは「これは誰のどの判断に効くか」で決める。1 文で答えられない記述は書かない。答えられるなら長くてよい。
- 1 つの主張は 1 箇所に置く。正本がある内容は写さず、正本を指す。写すと片方だけ古くなる。
- 背景は、無いと今の形が理解できない分だけ書く。

## Gotchas

- ADR には確定した判断だけを書く。「まだ実行していない」「次はこうする予定」を書くと、実行されなかった時に ADR が嘘になる。
- 既存の doc に規定を足す前に、既存の実態を数える。あるべき形を先に決めてから既存を見ると、大多数と食い違う規定ができる。`rg -c` や `ls` で数えてから、実態に合わせるか、意図して外して既存を直すかを選ぶ。

## 扱わないもの

- commit message（git-commit が扱う）。
- requirements / design / tasks のような事前の doc を作るか、仕様 doc をいつ更新するか。repo の運用に従う。
- 一次情報が無い内容を事実として書くこと。秘密情報、認証情報、private config、本番設定、未公開の個人情報。必要なら止まって確認する。
- 小さな変更のための doc 全体の書き直し。

doc が不要と判断した時も、その旨と理由を返す。
