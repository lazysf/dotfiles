# Feature Note Format

1 変更を 1 枚に縦へ積む既定の根拠 artifact。`docs/notes/<name>.md` を使う。
「上位の要件 → 中位の設計 → 下位の実装・検証」を 1 ファイルで上から下に辿れる形にする。
Level 2 / 3 の変更で使う。Level 1（typo / 1 行 / 自明）はノートを作らず、完了報告に要件 1 行と検証を残す。commit 依頼時だけ commit message にも反映する。

## Rules

- ノート用フォルダは増やさず、`docs/notes/<name>.md` を使う。`<name>` は変更を表す kebab-case。
- 1 変更 1 ノート。場所と章構成は常に同じに保つ。
- Level 2/3 開始時に lead が skeleton（要件 / 設計 / 実装・検証）を作り、各層は担当 agent が埋める。書き込みを担当しない agent の検証証跡と review 指摘・対応は lead が記録する。
- 受入条件は `AC-001` のような ID を振り、観測可能な結果として書く。検証はこの `AC-*` に対応付ける。
- 設計の主要判断は理由とともに書く。代替案は選択に影響した場合だけ残す。
- 検証は auto（test の path と結果）と manual（手順・期待値・実測値）を分け、対応する `AC-*` を明記する。auto は実装時に記録し、manual の実測値は inspector が確認して lead が記録する。manual の証跡は必要ならリンクで残す。
- 未確認事項は `未確認事項` に残し、確認済み前提と混ぜない。
- 不可逆・非自明で複数変更にまたがる判断は ADR へ切り出し、ここからリンクする。
- 規模が大きく PRD / 要件定義 / 基本設計 / 詳細設計 / Traceability Matrix を別建てする場合だけ、それぞれの format reference に従う。

## Template

```markdown
# [feature / 変更名]

## 要件

### 背景 / 目的

[なぜこの変更が必要か。確認済みの背景と達成したいこと。]

### 受入条件

- `AC-001`: [観測可能な受入条件。]

### 非目的

- [今回扱わないこと。]

## 設計

### 方針

[要件にどう応えるか。主要な判断と理由。]

### 構成 / インターフェース

- `[component]`: [責務、境界、外部 I/O、失敗時の扱い。]

### 検討した代替案

- [選択に影響した場合だけ。]

## 実装・検証

### 変更内容

- [変更した file と要点。]

### 検証

- auto: [`AC-*` に対応する test の path と結果。]
- manual: [`AC-*` に対応する手順・期待値・実測値。必要なら証跡リンク。]

### レビュー

- [quality / security review の指摘と採否・対応。なければ省略。]

## 未確認事項

- [未確認事項。]
```
