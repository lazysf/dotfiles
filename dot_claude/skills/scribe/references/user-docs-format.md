# docs/ の利用者向け doc 形式

`docs/` 配下に、利用者向けの詳しい doc（入門、使い方、設定の一覧、概念の説明）を作成・更新する時に読む。`docs/README.md`、ADR、notes はそれぞれの reference を読む。

## 置き場と命名

- `docs/` の直下に置く。ファイル名は内容を短く表す kebab-case。
- 件数が増えたら、種類ごとの directory に分ける。
- 既存の `docs/` が別の分け方をしていれば、そちらに従う。

## 構成

書く前に、doc の種類を次の 4 つから 1 つ選ぶ。分け方は [Diátaxis](https://diataxis.fr/start-here/) に従う。

| 種類 | 読み手 | 読み手が求めるもの | 書くもの |
| --- | --- | --- | --- |
| [tutorial](https://diataxis.fr/tutorials/) | 初めて学ぶ人 | 一通りやってみて身に付けること | 最初から最後まで通る 1 本の手順と、各段の結果 |
| [how-to](https://diataxis.fr/how-to-guides/) | すでに使える人 | ある目的を達すること | 前提、手順、結果の確かめ方 |
| [reference](https://diataxis.fr/reference/) | 調べに来た人 | 正確な一覧 | 設定キー、コマンド、引数、既定値 |
| [explanation](https://diataxis.fr/explanation/) | 理解したい人 | なぜその形か | 概念、仕組み、制約、代替案 |

- 1 つの doc に 2 つの種類を混ぜない。手順の途中に概念の説明を挟むと、手順を引きたい読み手が迷う。
- 他の種類の内容が要る時は、その種類の doc へリンクする。

## 書く規則

### tutorial

- 選択肢を出さず、1 本の道にする。選択肢は how-to と reference に任せる。
- 各段で、読み手に見える結果を示す。読み手は結果を見て、正しく進んでいると分かる。
- 最初から最後までを、書いた形のまま通す。途中で 1 つでも通らない段があると、学ぶ人は自分で直せない。
- 説明は最小にし、explanation へリンクする。

### how-to

- 題には目的を書く（「〜する」）。
- 読み手は基本を知っている前提で書く。条件で分かれる手順（「〜なら、〜する」）はよい。
- 網羅しない。全部の選択肢は reference に任せて指す。

### reference

- 製品の構造に沿って並べる。設定ファイルの順、コマンドの階層など。
- 記述だけを書く。例は置いてよいが、手順にしない。
- 実体の定義（schema、`--help` の出力、設定ファイル、型の定義）と突き合わせる。どの定義と突き合わせたかを doc に書く。定義と doc が食い違ったら、定義を正とする。
- 定義から生成できる一覧は、生成物を正本にして手で写さない。

### explanation

- 題は「〜について」の形にする。
- 理由、制約、利用者から見た代替案を書く。開発の経緯と、作る側の判断の比較は ADR と notes に置く。

### README との分担

- README には、導入と最小の使い方を残す。詳しい手順と一覧は `docs/` に置き、README から指す。
- 同じ手順を README と `docs/` の両方に書かない。片方だけ古くなる。例外は tutorial で、1 本の道を途切れさせないために README の導入の手順を含めてよい。その時は、README の導入を変えたら tutorial も合わせる。
- `docs/` に doc を足したら、`docs/README.md` の案内と、README からのリンクを確かめる。
