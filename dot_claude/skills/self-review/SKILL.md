# Self Review

変更を閉じる前に、自分の差分を自分で見直す。指摘が出なくなるまで直してから次へ渡す。

## 手順

1. `git status -sb` と `git diff`（staged があれば `git diff --staged` も）で変更の全体を読む。
2. 下の観点で見る。観点ごとに、何を確認して何が無かったかを持つ。
3. 見つけた指摘を直す。直したら 1 へ戻る。
4. 指摘が出ない巡が来ても、そこで止めずにもう 1 巡する。2 巡続けて出なければ「出力」の項目を返す。

**1 巡で終わらせない。** 直すと別の問題が生まれる。数値を消せば指示語が指す先を失い、記述を強めれば根拠を超え、短くすれば参照が空振りする。最初の巡には無かった問題が、直した後に現れる。

**指摘が 0 になった巡は、収束の証拠にならない。** 同じ角度で見ただけかもしれず、両者を区別する手がかりが無い。自分が書いた文は自分の意図で読めてしまうため、同じ読み方を繰り返すと最初からある問題を何巡も見逃す。指摘が出なかった次の巡は、意図を離れて字面だけで読む。

## 観点

### スコープ

- 全ての変更行が依頼にトレースできるか。ついで改善や無関係な整形が混ざっていないか。
- 依頼の範囲を狭めていないか。
- 性質の違う変更が 1 つに混ざっていないか。混ざっていれば commit を分ける。

### 事実

- 断定が観測を超えていないか。「できない」「必ず」「〜が原因」のような強い語だけでなく、`X の Y` を `X` へ、`〜の場合がある` を `〜する` へ広げる一段の拡張も、確かめていない範囲を含む。
- 推論を断定の形で書いていないか。推論なら推論と分かる形か。
- 数値と日付が今も成り立つか。実測値に測定時点が付いているか。

### 整合性

- 参照が空振りしないか。リンク先に、期待させた内容があるか。
- 1 つの概念に 1 つの語を使っているか。既存の表記に揃っているか。
- 変えた path、名前、設定キーが他の場所に残っていないか。`rg` で検索して確かめる。

### 過剰さ

- 消しても主張が変わらない記述がないか。
- 周囲と比べて長すぎる箇所がないか。長さの理由が情報量なら残してよい。
- 指示語が指す先を持っているか。

### doc

- 実装の変更に doc の追従が要るか。要否を黙って飛ばさない。
- notes が現在の設計を書いているか。変更履歴になっていないか。
- ADR の本文を書き換えていないか。

## 独立 context を提案する条件

自己確認は自分が書いた文を見るのは得意だが、自分が調べた範囲の外は見えない。一次情報を取り直す目が要る場面では `quality-reviewer` / `security-reviewer` agent を提案する。

- 実測や調査結果を根拠にした記述が多い。裏取りをやり直す価値がある。
- 契約、設定、skill / agent 定義など、間違うと影響が広い surface を触った。
- 2 巡しても指摘が出続ける。自分の盲点の可能性がある。

ユーザーが「じっくり」「独立で」と言った時、または agent 名を出した時は、提案を挟まず起動する。

## 問い合わせる条件

直し方が複数あり、選択で成果物が変わる時は、選択肢と推奨を示して聞く。自分で決めてよいのは、既存の実装や doc に寄せれば決まるもの。

- 情報を残すか短くするかのトレードオフ
- スコープを広げるかどうか
- 設計判断の変更を伴う直し

## 扱わないもの

read と自分の変更の修正だけを行う。commit、push、履歴の書き換えは扱わない。bug の検出は `/code-review`、security は `/security-review`。doc の作成・更新は `scribe`。

## 出力

| 項目 | 内容 |
| --- | --- |
| `scope` | 依頼と変更の対応。意図して外したもの |
| `findings` | 巡ごとに見つけた指摘と、直した内容 |
| `verification` | 観点ごとに何を確認して何が無かったか |
| `open_questions` | ユーザー判断を待っているもの |
| `next` | 次の工程（commit / agent 起動 / 追加作業） |

指摘が 1 件も出なかった場合も同じ項目を返す。`verification` を「確認した」で済ませない。何を見たかが書けないなら、まだ見ていない。
