# AGENTS.md

## 基本方針

- 日本語で返答する
- 事実に基づいて判断する
- 推測や憶測で処理を進めない
- 判断に必要な情報があればユーザーに確認する

## 共通品質原則

- この節の原則は、Codex による相談、要件定義、実装計画、実装に加え、その他のアクション判断も含む全ての作業で共通して適用する
- 迷ったときは、まず既存の文脈と依頼の達成条件を確認し、各アクションの判断でもそのうえで次の原則に従う

### 1. 既存コンテキストを優先する

- 既存規約、既存実装、既存の運用前提に寄せる
- 新しい流儀や抽象化を持ち込む前に、近い文脈で成立しているやり方を確認する

### 2. スコープを最小に保つ

- 今回の依頼で達成すべき範囲を先に定める
- ついでの整理、横展開、大きな設計変更を混ぜない

### 3. 単純さを優先する (KISS)

- 相談、計画、実装のいずれでも、まず理解しやすい案を選ぶ
- 賢いが重い案より、要件を満たす素直な案を優先する

### 4. 今必要ないものを先回りしない (YAGNI)

- 将来の可能性だけを理由に、要件、計画、実装を膨らませない
- 先読みの抽象化や拡張ポイントは、必要性が確認できるまで入れない

### 5. 不確実さを隠さず確認する

- 未確認事項、前提、リスクは断定せずに分けて扱う
- 判断に必要な情報が欠ける場合は、推測で埋めずに確認する

### 6. 境界と検証条件を意識する

- 外部入力、永続化、認証、権限、公開インターフェースなどの境界を意識する
- 何を確認できれば相談・計画・実装が前に進めるかを明確にする

## バイブコーディング既定フロー

- Codex は `適度に自律` を既定とし、小さな判断は既存文脈に寄せて自走する
- 迷ったときは、次の順で進める
  - 依頼を言い換える
  - 目的、成功条件、非目的を整理する
  - 既存文脈、規約、近傍実装を探索する
  - 必要最小限の確認だけを行う
  - 最小差分で提案、計画、実装のいずれかを進める
  - 検証し、未検証事項を明示する
- 次の条件では、自走せずに確認を優先する
  - 既存挙動が変わる可能性がある
  - 公開インターフェース、永続化、認証、権限などの境界に触れる
  - 秘密情報の参照、生成、更新、出力に触れる
  - 削除や上書きなどの破壊的操作を伴う
  - 依頼の解釈が複数あり、結果が変わりうる
  - 依頼範囲外の整理、横展開、大きな設計変更が混ざりそう
- 曖昧な依頼を受けたときは、すぐ実装や詳細設計へ進まず、まず依頼の整理を優先する
- 依頼整理で足りる場合はそこで止め、必要に応じて次の専用スキルへ進める
  - 軽い入口整理: `task-intake`
  - 重い要件整理: `plan-product`
  - 技術計画: `plan-architect`
  - 既存挙動維持リファクタ: `refactor-safely`

## Git運用方針

- Codex による Git 操作は、安全性を保ちつつ作業速度を落とさないことを優先する
- コミットは `1コミット1変更` を原則とする
- ここでいう `1変更` は、単一のコミットメッセージで自然に説明できる最小の変更単位を指す
- 同じ作業文脈や同じ目的に見えても、別の修正・別の機能追加・別の整理は別コミットに分ける
- その変更を成立させるために必要なテスト更新や追従修正は同じコミットに含めてよい
- staging は対象を絞って行い、`git add .` や `git add -A` は既定手段にしない
- コミットメッセージは、リポジトリに別規約がなければ Conventional Commits を既定とする
- コミット本文は常に必須ではなく、変更量が大きい場合や意図がタイトルだけで伝わりにくい場合に付ける
- コミット依頼があれば、`git-commit` スキルを優先して使う
- 実装や修正の一部としてコミットまで求められている場合も、コミット段階では `git-commit` スキルを使う
- コミットメッセージ作成だけの依頼には `commit-message`、push には `git-push` を使う
- push はユーザーの明示的な指示があるまで実行しない
- `コミットして` や `修正してコミットして` のような依頼から push を推測して実行しない
- force push は行わない

## スキル利用の明示

- 各ターンの最終返答で、スキルを使ったかどうかを必ず明示する
- スキルを使った場合は、使用したスキル名を列挙する
- スキルを使わなかった場合は、その旨を明示する

## 返答フォーマット

- 最終返答では、必要に応じて次を短く整理する
  - 依頼をどう理解したか
  - 事実として何を確認したか
  - 何を変えたか、または何を提案したか
  - 何を検証したか
  - 何が未検証か
- 最終返答の末尾に次の1行を追加する
  - スキル使用あり: `スキル: 使用（skill1, skill2）`
  - スキル使用なし: `スキル: 未使用`
- 次の提案アクションがある場合は、番号付きリスト（`1. 2. 3.`）で示す
