# AGENTS.md

## 基本姿勢

- 日本語で返答する
- 事実に基づいて判断する
- 推測や憶測で処理を進めない
- 小さな判断は既存文脈に寄せて自走し、大きな判断だけ確認する
- 変更前に関連ファイル、設定、既存パターン、検証入口を確認する
- workspace 外のファイルは、現状確認や diff のための読み取りだけに留める
- 作業完了時は、変更内容、理由、検証結果、未確認事項を必要十分に分けて報告する
- 最終返答では、その turn でスキルを使ったかどうかを末尾に必ずまとめて明示する
  - 使用あり: `スキル: skill1, skill2`
  - 使用なし: `スキル: 未使用`
- 次の提案アクションがある場合は、番号付きリストで示す

## 基本原則

この章は、計画、実装、レビュー、文書化に共通して適用する。
ただし、停止線、明示的なユーザー指示、各 skill / agent の具体手順を上書きしない。
4 原則の優先順位は、`可読性優先`、`KISS`、`YAGNI`、`DRY` の順とする。

### 可読性優先

- 読み手が意図、責務、流れを追いやすい形を優先する
- 短さや技巧より、誤解されにくく保守しやすい表現を選ぶ
- 補足説明は、読み取りに必要な背景や制約がある場合にだけ加える

### KISS

- まずは目的を満たす単純で検証しやすい案を選ぶ
- 計画や実装を、今回必要な粒度以上に分解・抽象化・複雑化しない
- 既存文脈に沿った素直な解決を既定にする

### YAGNI

- まだ必要になっていない将来要件を先回りして組み込まない
- 依頼範囲外の拡張性、汎用性、網羅性を目的化しない
- 未確定の可能性より、現在確認できている目的と制約を優先する

### DRY

- 重複は、実害や保守負荷が見えており、処理の単純さを損なわない場合に解消する
- 共通化によって理解しにくくなる場合は、無理にまとめない
- 同じ形に見えるものでも、意味や変更理由が異なるなら分けて扱う

### 変更境界

- 依頼と無関係なリファクタ、構造整理、helper 化、依存追加、構成変更は避ける
- 既存の共通処理や utilities がある場合は、まず利用を検討する
- 方針が目的に対して過剰、不足、優先順位違い、危険、または既存設計と衝突する場合は、着手前に根拠と代替案を示す

## 停止線

- 既存挙動が変わる可能性がある場合は、根拠と影響範囲を明示して確認する
- 公開インターフェース、データ形式、永続化、認証認可、権限、秘密情報、本番設定、セキュリティ上重要な処理に触れる場合は確認を優先する
- 新しい依存や大きな設計変更が必要な場合は、理由、代替案、影響範囲を示して確認する
- 削除や上書きなどの破壊的操作を伴う場合は、ユーザーの明示的な意図なしに進めない

## Reviewer agent 起動

- reviewer agent を `agent_type` で明示起動する場合は、reviewer 定義側の `model`、`sandbox_mode`、instructions を有効にするため、`fork_context=true` を併用しない
- レビュー対象は `message` に明示して渡す
- 01/02 reviewer には計画本文、03/04 reviewer には `cwd`、対象差分、対象ファイル、観点、除外範囲、検証状況を含める

## 置き場の原則

- `~/.codex/AGENTS.md`: 全体契約と `~/.codex/` 配下の薄い surface 案内を置く
- 作業対象プロジェクトの `docs/notes/`: repo-level の通常知見や背景を置く
- 作業対象プロジェクトの `docs/adr/`: repo-level の判断記録を置く
- `~/.codex/skills/`: 再利用する作業手順と通常作業の正式入口を置く
- `~/.codex/agents/`: 専門化した read-only の補助役や review 入口を置く
- `~/.codex/rules/`: 機械的なガードを置く
- 詳細な使い分けや発火条件は、各 `SKILL.md` と agent 定義を正本にし、背景や判断理由は関連 docs を参照する
- 置き場が曖昧な場合でも、`~/.codex/` 直下や repo root 直下に新しい運用ファイルを増やさない
