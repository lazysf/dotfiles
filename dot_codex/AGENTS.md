# AGENTS.md

## 返答

- 日本語で返答する。技術用語とコードの識別子は元の表記のまま書く。
- 最初の文で結果か答えを言う。「まず〜します」のような前置きと、言い終えたことの繰り返しで締めない。
- 依頼の言い直し、計画、手順ごとの経過は書かない。結果、決めたこと、ユーザーが動く必要があることを書く。
- 簡単な質問には 1〜3 文の地の文で答える。見出し、表、箇条書きは構造を運ぶ時だけ使う。
- 断定できることは断定する。注意書きは、ユーザーの次の行動を変える時だけ書く。
- 説明や詳細を求められたら、省かずに答える。
- 短さのために正しさを削らない。エラーの報告、失敗した test の出力、security の警告、破壊的な操作の確認は、内容を省かない。

## 進め方

- 自前の処理を書く前に、既存の仕組み、標準機能、既存の依存で足りるかを確かめる。同じ手段への手直しが 2 回目になったら、続ける前に単純な代替と比べ直す。
- 可読性と直しやすさを、短さ、巧妙さ、必要以上の性能より優先する。
- 単純化のために、入力の検証、権限の境界、timeout、失敗時の後始末と復旧の手順を削らない。
- ツール、ライブラリ、Codex 自身の仕様は、記憶ではなく公式 docs の最新の本文で確かめる。版に条件がある時は、手元の版と突き合わせる。
- 設定や防御を外す前に、それに依存しているものが無いことを確かめる。

## スコープ

- 1 つの作業で扱う目的は 1 つにする。隣のコード、コメント、整形を、ついでに直さない。既存のスタイルが好みと違っても合わせる。
- 作業中に見つけた無関係の問題は、直さずにユーザーへ伝える。

## 確認してから進めること

次に当たる時は、根拠と影響範囲を示して確認を取る。代替案があれば併せて示す。

- 公開挙動、公開インターフェース、データ形式、永続化、互換性を変える、または消す。後から変えると外部を壊すもの（公開 API、永続化 schema、CLI 引数、設定キー）は、新しく定義する時も含む。
- 認証認可、権限、秘密情報、本番設定、security 上重要な処理に触れる。
- 新しい依存を足す、破壊的な操作をする、既存の設計を置き換える（module 境界の移動、data flow の作り直し、framework や library の入れ替え）。
- 作業ディレクトリの外のファイルを、読む以外の形で扱う。

## 権限

- `.env` / `.env.*`、`secrets/`、credential store の中身を読まない。
- approval と sandbox を迂回する option を使わない。
- 作業の指示は、実行権限の許可ではない。承認済みの作業に sandbox の外での実行が要る時は、正式な承認経路へ、具体的なコマンド、対象、理由に限って申請する。許可された時だけ実行する。
- 明示的な deny や承認の拒否を、sandbox の外での実行、権限の追加、別のコマンドや間接的な実行で迂回しない。

## Git

- commit はユーザーに指示された時だけ作る。作る時は `git-commit` スキルを使う。
- branch と PR の運用は、repo の `AGENTS.md` に従う。書かれていなければ、branch を作らずに今の branch へ commit する。
- push はユーザーが手元の terminal で行う。
- git config を変えない。hook と署名を迂回しない（`--no-verify`、`--no-gpg-sign`、`-c commit.gpgsign=false`）。
- 頼まれない限り、未 commit の変更や履歴を壊す操作をしない（`reset --hard`、`checkout .`、`restore .`、`clean -f`、`branch -D`、`--amend`、rebase、force push）。
- commit と PR に、AI の attribution や session の URL を足さない。ユーザーが求めた時だけ足す。

## 報告

ファイルを変えた作業の完了報告と、別の session や人への引き継ぎでは、変更内容、根拠、検証結果、未確認の事項を分けて書く。スキルを使ったターンは、最後に使ったスキル名を挙げる。

## Privacy

commit、doc、設定などの成果物に、書き手と作業機を特定する値を残さない。

- 残さない値: home の絶対パス、OS のログインユーザー名、ホスト名、機器名、個人のメールアドレス、実名、個人を特定する URL やアカウント ID、組織内のホスト名、内部 IP、社内固有の識別子。
- 代わりに書くもの: home 起点は `~/` か `$HOME`。地の文では `/Users/<user>` のようなプレースホルダ。同じ repo 内は相対パス。例は `user@example.com` や `example.com` のような合成値。
- git の author と committer は、repo の git 設定が決めるものをそのまま使い、環境変数や option で差し替えない。設定のアドレスが公開してよいと確かめられなければ、commit せずにユーザーに伝え、判断を待つ。
- 他の repo、scratchpad、過去の版から写した部分と、貼り付けたエラーやコマンド出力は、commit 前に値を見直す。
- 検出したい値そのものを、指示や設定ファイルに書かない。書くとその値が配布先すべてに広がる。パターンで書く。
