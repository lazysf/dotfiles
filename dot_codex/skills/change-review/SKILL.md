# Change Review

高品質なバイブコーディングのための、出口専用レビュースキル。
目的は、変更後に「何が問題か」「何が未確認か」を短く正確に整理すること。

## 前提

- [AGENTS.md](../../AGENTS.md) の検証と報告の基準を前提に適用する。
- 変更内容と検証結果が確認できることを前提にする。

## 目的

- 変更後の自己レビューを標準化する。
- review agent を使う条件を明確にする。
- 指摘がある場合は findings-first で返し、ない場合も残リスクを明示する。

## 対象

- 実装後の最終確認。
- 複数ファイル変更や境界変更を含む差分。
- 変更内容をユーザーへ返す前の品質整理。

## 対象外

- 実装前の設計レビュー。
- ドキュメントだけの軽微更新で、レビュー判断が不要な依頼。

## 基本方針

- まず自己レビューし、必要時のみ review agent を使う。
- 問題があれば findings-first で返す。
- 問題がなくても、未検証事項や残リスクは隠さない。

## 進め方

### 1) 事前条件をそろえる

- 次の 4 点を確認してからレビューに入る。
  - 差分またはレビュー対象の境界
  - 実施済みの検証
  - 未検証事項
  - 今回レビューしない範囲
- 差分境界が曖昧な場合は、推測で全体レビューへ広げない。
- 検証結果がない場合は、レビュー不能ではなく `未検証` として明示する。

### 2) まず自己レビューする

- 次の観点を短く確認する。
  - 品質: 可読性、命名、例外処理、仕様逸脱、変更影響
  - セキュリティ: 入力検証、認証認可、情報漏洩、権限境界、外部 I/O
  - テスト/検証: 実施済み確認、抜けている確認、再現条件
  - 境界/影響範囲: 外部入力、永続化、公開インターフェース、近傍機能への波及
- 単一ファイルの軽微変更で、上記観点に強い懸念がなければ自己レビューのみで止めてよい。

### 3) 必要時のみ review agent へ上げる

- 次のいずれかに当てはまる場合のみ `review-quality` または `review-security` を使う。
  - 複数ファイル変更で追跡が難しい
  - 公開インターフェース、永続化、外部 I/O、権限境界などの境界変更がある
  - 認証認可、入力処理、秘密情報、ファイル操作、外部 API に触れる
  - 変更影響が広く、自己レビューだけでは見落としが不安
- `review-quality` は品質、仕様整合、テスト不足、変更影響の確認に使う。
- `review-security` はセキュリティや権限境界の確認に使う。
- 将来、対象言語固有の観点が `review-quality` だけでは不足すると確認できた場合に限り、言語別 reviewer の追加を検討する。

### 4) 出力を findings-first でまとめる

- 指摘がある場合:
  - `critical` / `high` / `medium` / `low` の順で findings を並べる
  - その後に open questions と residual risks を分けて添える
- 指摘がない場合:
  - `重大な指摘なし` を明示する
  - 実施済み検証、未検証事項、残リスクがあれば続ける
- 推測だけの懸念は findings にせず、`open_questions` または `residual_risks` に落とす

## 出力ガイド

- レビュー結果には次を短く含める。
  - 対象差分または対象範囲
  - 実施済み検証
  - findings または `重大な指摘なし`
  - open questions
  - residual risks
- 固定閾値で機械的に判定しない。既存規約や近傍実装に照らして重み付けする。
