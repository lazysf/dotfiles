# Implementation Guardrails

実装ループの中で迷いやすい判断を、既存コンテキスト優先でそろえる。

## 基本原則

### 可読性優先

- 名前、責務、構造、コメントは、あとから読む人が意図を追いやすいことを優先する
- 命名、責務の切り方、エラー処理、テスト配置は近傍実装に寄せる
- コメントは、見れば分かる処理ではなく、制約や意図がないと読み取りにくい箇所にだけ置く
- 行数目標のためだけに関数分割しない

### KISS

- まずは依頼を満たす最小の変更から始める
- 最初は理解しやすく検証しやすい最小案を選ぶ
- 近傍実装と明示規約に沿う素直な実装を既定にする
- 外部入力、公開面、永続化、権限、秘密情報などの境界を優先して堅くする

### YAGNI

- 将来前提の抽象化、設定、拡張ポイントを追加しない
- 内部処理では、必要以上の防御コードや設定層を増やしすぎない
- 理由の薄いラッパーや helper を増やさない
- 依頼範囲外の広域リネームや横展開を混ぜない

### DRY

- 実害のある重複だけを解消し、将来のためだけの共通化は入れない
- 抽出や共通化で引数や分岐が増えるなら、その時点では重複を残してよい
- 共通化で可読性や責務が悪化するなら、無理にまとめない

## 優先順位

1. リポジトリの明示規約
2. 近傍実装の書き方
3. 今回の依頼を満たす最小差分

## 実装時のガードレール

- 外部入力、公開面、永続化、権限、秘密情報などの境界を優先して堅くする
- 失敗しうる境界では、何が失敗したか追える形を残す
- 未検証事項を暗黙に成功扱いせず、実行できた確認と未検証事項を分けて扱う

## 避けること

- 将来前提の抽象化や拡張ポイントの追加
- 理由の薄いラッパーや helper の増殖
- 依頼範囲外の広域リネームや横展開
- 未検証事項を暗黙に成功扱いすること

## 仕上げ前の確認

- 今回の依頼を満たす最小差分に留まっている
- 近傍実装と明示規約に沿った書き方になっている
- 境界の入力、失敗時の扱い、既存契約の破壊有無を確認した
- 実行できた確認と未検証事項を説明できる
