# Coding Standards

高品質なバイブコーディングを実現するための、薄く強いガードレール。
目的は「速く雑に作る」ことではなく、「小さく、安全で、レビューしやすい差分を速く出す」こと。

## 前提

- [AGENTS.md](../../AGENTS.md) の共通品質原則を前提に適用する。
- `AGENTS.md` は全体原則と進め方、このスキルは実装時の設計・記述・抽象化・検証の詳細判断を扱う。
- 言語別ベストプラクティスは補助資料として扱い、repo 固有規約や近傍実装と衝突する場合は既存コンテキストを優先する。

## 目的

- 既存プロジェクトに自然になじむ変更を出す。
- 要件達成に必要な最小差分で実装する。
- 境界だけを十分に堅くし、内部は過剰設計しない。
- 検証結果と未検証事項を明確にする。

## 対象

- コード、スクリプト、設定を含む実装作業。

## 対象外

- ドキュメント更新のみの依頼。
- レビュー専用の依頼。

## 優先順位

判断が衝突したら、次の順で優先する。

1. リポジトリの明示規約
2. 既存実装のローカルな慣習
3. [AGENTS.md](../../AGENTS.md) の共通品質原則と、このスキルの実装適用

## Core Principles

### 1) Readability First

- コードは書かれる回数より読まれる回数の方が多い前提で判断する。
- 変数名、関数名、責務の切り方は、あとから読む人が意図を追いやすいことを優先する。
- コメントで補う前に、名前や構造で自己説明できる形に寄せる。
- フォーマットや書き方は、既存の一貫性を崩さない。

### 2) KISS

- まずは実際に要件を満たす、最も理解しやすい案を選ぶ。
- 賢いが重い案より、素直に読めて検証しやすい案を優先する。
- 過剰設計や早すぎる最適化は避ける。
- 最適化や抽象化は、必要性が差分から確認できるときだけ行う。

### 3) DRY

- 実害のある重複だけを解消する。
- copy-paste により修正漏れや仕様ずれが起きる重複は、関数、utility、共通部品への切り出しを検討する。
- 複数モジュールで繰り返される共通知識は、責務が保てる範囲で共有する。
- 推測的な抽象化や、将来のためだけの共通化は入れない。
- 共通化で引数、分岐、設定が増えて読みにくくなるなら、その重複は残してよい。

### 4) YAGNI

- 今必要な要件に直接効かない拡張ポイントは足さない。
- 将来使うかもしれない設定、抽象層、汎用ヘルパーは必要性が確認できるまで保留する。
- 複雑さは必要になった時にだけ足す。
- まずは最小の実装で通し、必要になったらリファクタで見直す。

## 実装判断の標準

### 1) 最小差分で進める

- 今回の依頼を満たす最小の変更から始める。
- ついでのリネーム、横展開、広域リファクタは別変更に分ける。
- 壊れている箇所とその近傍を優先して直す。

### 2) 既存に寄せる

- 新しい流儀を持ち込む前に、近くの実装の書き方を観察する。
- 命名、責務の切り方、エラーの返し方、テストの置き方は既存に合わせる。
- 正しさに直結しない個人流の整理は混ぜない。

### 3) 境界だけを堅くする

- 外部入力、永続化、ネットワーク、ファイルI/O、公開APIなどの境界で破綻しないようにする。
- 入力検証、エラーハンドリング、ログは境界を優先して整える。
- 閉じた内部処理では、防御コードを過剰に増やしすぎない。

### 4) 深いネストを避ける

- 条件分岐が積み上がる前に、早期 `return` や条件の切り出しを検討する。
- ネストを減らすための小さな分割は有効だが、1回しか使わない曖昧な helper を増やしすぎない。

### 5) マジックナンバーを放置しない

- 閾値、待ち時間、上限値など、意味を持つ値は名前を付けられるかを確認する。
- ただし、定数化のためだけに設定層や共通定数ファイルを増やさない。
- 近傍実装がインライン値でそろっている場合は、その文脈も尊重する。

### 6) 長い関数は責務で分ける

- 関数が長いこと自体より、責務が混ざって読みにくいことを問題として見る。
- 入力変換、計算、永続化、表示整形が混ざるなら、責務単位で分けられるかを考える。
- 行数目標のためだけに分割しない。

### 7) 明示的に失敗を扱う

- 失敗しうる境界では、何が失敗したか追える形で扱う。
- 例外やエラー値を握りつぶさず、呼び出し側や利用者が判断できる文脈を残す。
- 詳細な失敗情報が必要な場所と、簡潔で十分な場所を分ける。

### 8) 未検証は断定しない

- 変更に近いテスト、lint、build、スモークテストを優先する。
- 実行できなかった確認は隠さず報告する。
- 検証できていない箇所は、断定せず未検証として扱う。

## 実装で避けること

- 要件達成に不要な抽象化、拡張ポイント、設定層を足すこと
- 将来のためだけの設定項目や共通化を入れること
- 数値目標のために機械的に分割すること
- 理由の薄いコメントやラッパーを増やすこと
- 言語や近傍実装に合わない固定ルールを、一般論として持ち込むこと

## 実装フロー

### 1) 規約と周辺実装を読む

- 既存規約と、変更対象の近傍コードを確認する。
- 共通判断で足りない場合だけ、対象言語に対応する reference を追加で読む。

### 2) 変更範囲を絞る

- 目的と非目的を分ける。
- 変更境界を短く言語化する。

### 3) 最小実装で直す

- まずは素直な実装で通す。
- 抽出や共通化は、必要性が差分から明確なときだけ行う。

### 4) 境界と回帰を確認する

- 入出力境界、失敗時の挙動、既存契約の破壊有無を確認する。
- 必要に応じてテストや手動確認を追加する。

### 5) 結果を明示する

- 何を変えたか、何を確認したか、何が未確認かを短く整理する。

## コメントと抽象化の扱い

- コメントは「見れば分かること」ではなく、「見ただけでは分からない制約」を書く。
- 関数抽出や共通化は、重複や責務の混在が実際にレビュー負荷を上げているときだけ行う。

## 言語別 reference の読み分け

- 共通判断で足りる依頼は、この本文までを主とし、迷いどころだけ [references/vibe-coding-heuristics.md](references/vibe-coding-heuristics.md) を参照する。
- `Python` 実装で迷う場合は [references/python-best-practices.md](references/python-best-practices.md) を読む。
- `Lua` 実装で迷う場合は [references/lua-best-practices.md](references/lua-best-practices.md) を読む。
- `Shell`、`zsh`、`bash` を扱う場合は [references/shell-best-practices.md](references/shell-best-practices.md) を読む。
- `TOML` や設定ファイル編集で迷う場合は [references/toml-best-practices.md](references/toml-best-practices.md) を読む。
- 将来の言語追加は `references/<language>-best-practices.md` を増やし、この節に 1 行だけ導線を足す。

## 確認が必要なとき

- 要件が曖昧なとき。
- 既存挙動を変える可能性があるとき。
- 外部API、データ形式、マイグレーション、権限、セキュリティに影響するとき。
