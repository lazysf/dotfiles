# Vibe Coding Heuristics

`coding-standards` 本文だけでは判断しづらい場面のための補助資料。
ここに書く内容は必須ルールではなく、迷ったときの目安。
この文書では、実装時の迷いどころだけを扱う。

## まず疑うこと

- その抽象化は、今回の差分で本当に必要か。
- その整理は、いま直している不具合や要件達成に効くか。
- その分割は、読みやすくするためか、数値目標を満たすためだけか。
- そのコメントは、コードを読めば分かることではないか。

## 既存に寄せるときの見方

- 同じ責務の関数がどう命名されているか。
- エラーを `throw` / return / result 型のどれで扱っているか。
- 境界でどこまでバリデーションしているか。
- テストが unit / integration / snapshot のどこに置かれているか。
- 似た変更で、どの粒度までリファクタを許容しているか。

## 関数抽出してよい場面

- 同じ意図の処理がすでに2か所以上あり、今後も同じ責務で使う見込みが高い。
- 1つの関数の中で、入出力と計算と永続化が混ざって読みづらい。
- 名前を付けると、呼び出し側の意図が明確になる。

## 関数抽出しない方がよい場面

- 1回しか使わない短い処理で、抽出するとかえって視線移動が増える。
- 抽出後の関数名が「doThing」「handleData」のように曖昧になる。
- 抽出理由が「長いから」だけで、責務分離や再利用の実益が薄い。

## 共通化してよい場面

- バグ修正や仕様変更を同時に複数箇所へ適用する必要がある。
- 定数、変換ルール、権限制御のように、ずれると危険な知識が重複している。

## 共通化しない方がよい場面

- いまは似ているが、責務や変化理由が別。
- 将来の拡張を見越しただけで、まだ呼び出し側が1つしかない。
- 共通化すると引数やオプションが増えて、呼び出しの方が分かりにくくなる。

## バリデーションの目安

### 強く入れる場所

- HTTP/CLI 入力
- 設定ファイルの読み込み
- DB や外部APIとの境界
- 永続化前のデータ整形

### 入れすぎない場所

- 同一モジュール内で直前に保証された値を受け取る内部関数
- 一時的な変換ヘルパー
- 失敗しても局所的にすぐ原因が分かる閉じた処理

## エラーハンドリングの目安

- 境界では、利用者や呼び出し側が判断できる形で失敗を返す。
- 内部では、回復しないなら無理に包み替えず素直に伝播する。
- ログは、重複記録より責任境界を意識して置く。

## コメントの目安

### 書くとよい

- 外部仕様に由来する制約
- 一見すると不自然だが必要な分岐
- 将来消す前提の暫定対応

### 書かない方がよい

- 行ごとの動作説明
- 関数名を言い換えただけの説明
- コミットメッセージに残すべき変更理由

## テスト追加の目安

- バグ修正なら、まず再現ケースを足せるか考える。
- 分岐を増やしたら、その分岐だけは最小限で押さえる。
- リファクタなら、既存テストで守れる範囲を優先し、不足時のみ追加する。
- 重いE2Eより、変更点に近いレイヤーの検証を優先する。

## 典型的な避けたい挙動

- 小さな不具合修正で、関連の薄いファイルまで整形し始める。
- 命名統一のために広範囲な rename を混ぜる。
- 将来使うかもしれない設定項目や hook を先に追加する。
- 「きれいにする」ことが主目的になり、依頼の完了条件がぼやける。
