# Coding

## 本命の処理を先に通す

- 依頼の中心になる処理を、まず正常系で最後まで動かす。起き得る失敗や細かい分岐を、最初から全部処理しようとしない。先回りの対応が積み上がると、本命の実装が進まない。
- 処理しない失敗は、握りつぶさずに上へ伝える（例外を投げる、エラーを返す、非 0 で終わる）。何もしない `catch`、黙って既定値に逃がす処理、log だけ出して先へ進む処理は書かない。失敗が見えていれば、後から必要な処理だけを足せる。
- 個別の失敗処理を足すのは、依頼が求める時、実際に起きた失敗がある時、信頼境界の入力（外部からの値、ファイル、network）を受ける時。境界での入力の検証、外部呼び出しの timeout、失敗時の後始末は、最初の実装から省かない。

## 検査を通す

- 変更したら、repo の検査（lint、type check、test、build）を実際に走らせる。コマンドは repo の `AGENTS.md`、`package.json`、`Makefile`、CI の設定から探す。変更に関係する一番狭い範囲から走らせる。
- 検査が落ちたら原因を直す。検査を弱めて通さない（test の skip、assertion を緩める、ignore や除外を足す、期待値を出力に合わせて書き換える、test の対象そのものを mock で置き換える）。直せない時は、弱めずに止まって報告する。
- 走らせられなかった検査は、未検証として報告する。

## 既存ファイルの形式を保つ

- 既存ファイルの charset、改行（CRLF / LF）、BOM、インデントを変えない。変わると diff がファイル全体に広がり、読み違えられる形式もある（Windows PowerShell は、BOM の無い UTF-8 のスクリプトを ANSI のコードページで読む）。
- 既存ファイルは、変える箇所だけを直す。ファイル全体を書き直すと、BOM や改行が黙って変わる。
- 新しいファイルは、repo の `.editorconfig` や `.gitattributes`、同じ種類の既存ファイルに合わせる。

## コメント

- コメントには「なぜ」を書く。コードを読めば分かる「何を」は書かない。
- 意図して簡略化し、既知の上限を残した箇所は `tradeoff:` で始め、上限と作り直す条件を書く。条件が無いと、後から読んだ人が今も妥当か判断できない。例: `# tradeoff: 全体 lock。throughput が問題になったら口座ごとの lock へ`
- security に関わる上限は `tradeoff:` で閉じない。`AGENTS.md` の「確認してから進めること」に当たるので、コメントに残さずユーザーに確認する。

## 重複

まとめるのは、変える理由が同じ重複だけ。見た目が似ていても、意味や変える理由が違うコードは別々に残す。無理に共通化すると、片方の変更がもう片方を壊す。
