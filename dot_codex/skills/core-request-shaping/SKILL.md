# Request Shaping

Plan 工程の内部手順として、散らばった相談を実装や探索に渡せる短いブリーフへ整える。
目的は、散らばった相談を `実装や探索に渡せる短いブリーフ` に整えること。
フェーズ全体の入口は `phase-plan` を参照する。

## 前提

- [AGENTS.md](../../AGENTS.md) の契約と停止線を前提に適用する。
- まだ実装や詳細計画へ入る前の依頼整理として使う。

## 目的

- 曖昧な依頼を、Codex が扱いやすい入力へ整える。
- `目的 / 確認済み事実(Context) / 制約` を芯として短くそろえる。
- 仮定や未確定事項を切り分ける。
- 相談の初動で、不要な往復を減らす。

## 基本方針

- 情報を増やすより、今回必要な芯を残す。
- 未確認事項は断定せず、確認が必要な点として分離する。
- 解決策を決め打ちする前に、依頼の目的と制約を揃える。
- `core-task-intake` を置き換えず、入口で依頼品質を上げる役割に徹する。
- このスキルは依頼文の整形と主題の圧縮を担い、停止線の固定は `core-task-intake` に委ねる。
- これらの観点はユーザーに必須入力を求めるためではなく、このスキルが内部で依頼を正規化するための整理軸として使う。

## 対象

- 目的はあるが、依頼文が散らばっている相談。
- 背景や要望が複数混ざっていて、今回の主題を絞りたい依頼。
- まず `どう頼めばよいか` を整えたい相談。

## 対象外

- そのまま実装へ入れるほど具体的な依頼。
- 実装順序や影響範囲を技術計画として詰める依頼。

## 整形の観点

### 1) 依頼の主題を一文に縮める

- いま何を前に進めたい相談かを一文で言い換える。
- 要望が複数ある場合は、今回の主題と補足に分ける。

### 2) 事実と要望を分ける

- 既に確認済みの事実と、これから叶えたい要望を分ける。
- 憶測や一般論を事実として混ぜない。

### 3) 制約を置く

- 触ってよい範囲、避けたい変更、期限、互換性などの制約を先に拾う。
- ユーザーが明示していなくても、ユーザー発話や既存文脈から直接読み取れる制約は補ってよい。
- 推定を含むものは制約として確定せず、`仮定` または `未確定事項` に分ける。

### 4) 仮定と確認必須事項を分ける

- 補完根拠が弱いものは `仮定` として扱う。
- 補完できないものは `未確定事項` として残す。
- 質問は、答えによって計画や結果が変わる重要点だけに絞る。
- 既存挙動変更、公開面、永続化、権限、秘密情報、破壊的操作に触れる不明点は明示する。
- 小さな不明点は後続スキルに渡せる形にする。

## 後続への渡し方

- 通常は `core-task-intake` へ渡す。
- `core-task-intake` を省略するのは、探索対象と停止線がすでに明確な場合だけにとどめる。
- 成功条件や非目的の整理が重い場合は `core-product-planning` を検討する。
- 要件が固まっていて実装順序を詰めたい場合は `core-implementation-planning` を検討する。

## 出力ガイド

- 出力は次の項目に絞る。
  - 目的
  - 確認済み事実
  - 制約
  - 仮定
  - 未確定事項
  - 次アクション
- 各項目は短く保ち、長い仕様書にしない。
- 詳細な整形例が必要なら [references/request-shaping-templates.md](references/request-shaping-templates.md) を参照する。
