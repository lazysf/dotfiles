# Docs Update

高品質なドキュメント更新のための、薄く強いガードレール。
目的は「文章を増やすこと」ではなく、「実装事実に合う必要十分な記述を、既存文脈に沿って入れること」。

## 目的

- 実装や運用の変更を、読者が迷わない形で反映する。
- 仕様、実装、運用文書の同期を保つ。
- 既存ドキュメントの流れと用語を壊さずに更新する。
- 更新範囲を広げすぎず、必要な差分だけを入れる。

## 対象

- README、CONTRIBUTING、運用手順、セットアップ手順、設計メモなどの更新。

## 対象外

- 軽微な表記修正だけで、更新方針の整理が不要な場合。
- ドキュメントのレビュー専用依頼。

## 優先順位

判断が衝突したら、次の順で優先する。

1. 実装・設定・実行結果などの一次情報
2. 既存ドキュメントの構成・用語・明示規約
3. このスキルの原則

新しい書き方を持ち込むより、今ある文脈に自然につなぐことを優先する。

## コア原則

### 1) 事実から書く

- コード、設定、実行結果、運用前提を根拠に記述する。
- Issue や会話ログは補助情報として扱い、一次情報と矛盾したら採用しない。
- 未確認事項は断定せず、確認待ちとして扱う。

### 2) 既存文脈に寄せる

- 近い章の文体、用語、粒度、見出しレベルに合わせる。
- 既存の導線を壊さない場所に差し込む。
- 小さな変更で全面リライトしない。

### 3) 読者の次の行動を明確にする

- 誰向けの手順かを意識する。
- 前提条件、順序、期待結果、注意点を必要な範囲で書く。
- 読者が「次に何をすればよいか」で迷わないようにする。

### 4) 差分を最小にする

- 今回の変更に必要な記述だけを更新する。
- ついでの用語統一や構成変更は、必要性が高い場合だけ行う。
- 関連が薄い章まで広げない。

### 5) 検証可能にする

- リンク、コマンド、パス、参照先は可能な範囲で確認する。
- 実行できなかった確認は隠さず明示する。
- 手元で確かめていない手順を、確認済みのように書かない。

## 更新フロー

### 1) 何が変わったかを整理する

- 実装差分、仕様変更、運用変更を把握する。
- 誰に影響する更新かを整理する。

### 2) どこに差し込むか決める

- 新規追加より、既存の自然な位置への差し込みを優先する。
- 読者が探しやすい場所を選ぶ。

### 3) 必要十分に書く

- 手順、注意点、前提条件を過不足なく書く。
- 実害のない説明の増築は避ける。

### 4) 事実照合する

- リンク、パス、コマンド、参照関係を確認する。
- 他文書との用語や手順のずれを確認する。

## 更新時に避けること

- 小さな変更に合わせてドキュメント全体を書き直す。
- 実装で未確認の内容を断定して書く。
- 読者や対象環境を曖昧にしたまま手順を書く。
- 単なる文章好みで広範囲に触る。

## 出力ガイド

- 何を変えたか、どこに反映したか、何を確認したかを簡潔に示す。
- 未確認事項があれば隠さず示す。
- 実行が必要な手順や注意点があれば短く添える。
