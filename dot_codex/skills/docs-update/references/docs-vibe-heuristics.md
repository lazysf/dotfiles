# Docs Vibe Heuristics

`docs-update` の本文だけでは判断しづらい場面のための補助資料。
ここに書く内容は必須ルールではなく、迷ったときの目安。

## まず疑うこと

- その記述は、実装や設定で裏取りできているか。
- その説明追加は、今回の変更に本当に必要か。
- その章を直すより、近い別の章に追記した方が自然ではないか。
- その改善は、読者の失敗を減らすのか、単なる好みなのか。

## 読者の詰まりどころ

- 必須ツールや認証の前提が抜けていないか。
- 対象OSや前提環境が曖昧でないか。
- 手順の順序が実際の実行順と合っているか。
- 成功時の期待結果や確認方法が抜けていないか。
- 失敗しやすい分岐や注意点が必要なのに省かれていないか。

## 差し込み先の見方

- その情報を最初に必要とする位置はどこか。
- セットアップ、更新、トラブルシュートのどこに属するか。
- 既存の見出しや箇条書きに追記する方が自然か。
- 新しい章を立てるほど独立した話題か。

## 強く確認したい項目

- コマンドが存在し、文法的におかしくないか。
- パスやファイル名が実在するか。
- 相対リンクや参照先が有効か。
- 他文書と用語や手順が矛盾していないか。
- セキュリティや破壊的操作に関わる注意喚起が不足していないか。

## 書き足しすぎないための目安

- 今回の差分で影響しない章まで触らない。
- 「あると親切」だけで長い補足を増やしすぎない。
- 実装がまだ固まっていない内容を将来前提で書かない。
- 同じ意味の説明を複数箇所に複製しない。

## 文書タイプ別の着眼点

### README

- 初回導線が切れていないか。
- 最短手順が埋もれていないか。
- 新規利用者が最初の成功まで進めるか。

### CONTRIBUTING / 開発ガイド

- 開発者がローカル検証を再現できるか。
- 実際の運用とズレた規約を書いていないか。

### Runbook / 運用手順

- 実行順序と停止条件が明確か。
- 失敗時の戻し方や迂回策が必要か。

### 設計メモ / ADR

- 背景、判断、影響範囲が分かるか。
- 現行実装との関係がぼやけていないか。

## 指摘を弱めるべき場面

- 単なる言い回しの好み。
- 既存文体に合わせた結果の表現差。
- 実装事実には影響せず、読者の失敗も増やさない差異。
