# Git Commit

Gitの変更を安全にコミットする依頼に対応する。

## 基本方針

- 対象が不明なら確認する。
- 破壊的操作は行わない。
- Git の書き込み系操作は逐次実行する。
- `git add`、`git commit`、`git status`、`git diff --cached` など `.git/index.lock` と競合しうる操作は、完了を待ってから次へ進む。
- コミットフローでは、Git 操作を並列に投げない。
- detached HEAD の場合は停止し、どのブランチでコミットするか確認する。
- rebase・merge・cherry-pick・revert 中やコンフリクトがある場合は停止して確認する。
- 未追跡ファイルや大きな生成物、バイナリ、機密情報が含まれる場合は対象を確認する。
- リポジトリの規約（README・CONTRIBUTING・テンプレ）があれば優先する。
- `--amend` や履歴の書き換えは指示がない限り行わない。
- ステージ対象は、合意した1変更の範囲に限定する。
- Codex がこのスキルでコミットを実行する場合は、非対話で完結させる。
- エディタ起動を前提にした `git commit` 単独実行は避け、`-m` または `-F` を使う。
- `git add .`、`git add -A`、`git add --all` のような broad add は既定手段にしない。
- `git add -p` は必要なときだけ使い、日常フローの前提にはしない。
- 無関係な変更が混在する場合は、コミットを実行せず分割方針の合意を先に取る。
- 異なる変更は同一コミットに混ぜない。
- 複数コミットが必要な場合は、1件ずつ順に処理する。

## コミット分割の原則

- 1コミット1変更を原則とする。
- ここでいう1変更とは、単一のコミットメッセージで自然に説明できる最小の変更単位を指す。
- 同じ作業文脈や同じ目的に見えても、別の修正・別の機能追加・別の整理は分ける。
- 片方だけを取り消したくなりそうな変更は分ける。
- その変更を成立させるために必要なテスト更新、参照更新、追従修正は同じコミットに含めてよい。
- ドキュメント更新と設定変更、別件の修正同士、準備リファクタと本体変更のように独立してレビューできる変更は分ける。

## 対象外

- プッシュのみが目的の依頼（git-push を使用）。
- コミットメッセージの作成・推敲のみが目的の依頼（commit-message を使用）。
- 変更が存在しない状態でのコミット要求。

## 本文の判断

- コミット本文が必要かどうかは、このスキル内で staged diff を見て判断する。
- リポジトリ規約やユーザー指定があればそれを最優先する。
- 規約がない場合は、次のいずれかに当てはまれば本文を付ける。
  - 変更ファイル数が多い。
  - 変更行数が多い。
  - 変更理由がタイトルだけでは伝わりにくい。
  - 設定変更、運用変更、移行、依存更新などで影響説明が欲しい。
- 小さく自明な変更、rename-only、format-only ならタイトルだけでもよい。
- 迷う場合は本文を付ける。

## コミットメッセージの扱い

- コミットメッセージは、リポジトリに別規約がなければ Conventional Commits を既定とする。
- 言語はリポジトリ規約を優先し、規約がなければ英語を既定とする。
- スコープは既定では省略し、まず scope なしで成立する案を優先する。
- スコープは、識別上の実益が明確にある場合や、リポジトリ規約で要求される場合にのみ付ける。
- なんとなく対象ディレクトリやモジュール名が見えるだけでは付けない。付けないと意味が弱くなる場合に限って付ける。
- ユーザーがメッセージを指定した場合も、必要に応じて軽く整形・妥当性確認を行う。
- メッセージ未指定時は、このスキル内で最終案を1件だけ組み立てて使う。
- 書式や例が必要な場合のみ `commit-message` スキルや `commit-message-format.md` を補助的に参照する。
- コミット実行の正規ルートはこの `git-commit` スキルとし、別のコミット専用 agent を前提にしない。

## 手順

### 1) 状態確認

- `git status -sb` で状態を確認する。
- この確認が完了するまで、次の Git 操作を開始しない。
- rebase・merge・cherry-pick・revert 中やコンフリクトがある場合は停止して確認する。

### 2) 変更有無の判定

- 変更がない場合は「コミット対象がない」旨を伝えて終了する。

### 3) 変更内容の確認

- `git diff` で変更内容を確認する（対象が不明なら質問する）。
- 変更を変更単位で分類し、複数の変更が混在している場合はコミットを停止して分割方針を合意する。
- 未追跡ファイルや大きな生成物、バイナリが含まれる場合は対象を確認し、必要なら除外を提案する。
- 合意前に `git add -A` やコミットを実行しない。

### 4) ステージ

- 指定がなければ、合意した1件のコミット候補、つまり1変更の範囲のみをステージする。
- 指定があれば `git add <paths>` などのパス指定ステージを優先し、その範囲のみステージする。
- 1ファイル内に複数の変更や複数コミット候補が混在する場合は、まずファイル分割や差分整理で非対話に分離できるか検討する。
- 非対話で安全に分離できる場合に限り、対象範囲のみをステージする。
- 非対話で安全に分離できず、`git add -p` に依存しないとコミット境界を守れない場合はコミットを停止し、差分整理または分割方針の合意を優先する。
- ステージ後の確認は、`git add` の完了を待ってから行う。

### 5) ステージ内容の確認

- `git diff --staged` でステージ内容を確認する。
- ステージ内容がコミット候補の変更単位と一致しない場合は、コミットを中止してステージを見直す。
- 必要なら `git diff --staged --numstat` や `--stat` でファイル数・変更量も確認する。
- この確認が完了するまで、`git commit` を開始しない。

### 6) メッセージ作成

- staged diff を見て、タイトルだけで十分か本文を付けるかを決める。
- 本文を付ける場合は、Why / What / Impact を短くまとめる。
- 形式や wording に迷う場合だけ `commit-message` を補助的に使う。

### 7) コミット

- タイトルだけで十分なら `git commit -m "<header>"` を使う。
- 本文が1段落なら `git commit -m "<header>" -m "<body_text>"` を使う。
- 本文が複数段落、またはフッターを含む場合は、整形済みメッセージを一時ファイルに書いて `git commit -F <file>` を使う。
- コミット直前に staged diff を再確認し、想定とずれていたら手順 5) に戻る。
- 必要なら `git log -1 --oneline` でコミット結果を確認する。
- コミット失敗時はエラー内容をそのまま示し、再実行前に原因（hook失敗、整合性エラー等）を確認する。
- コミット中や hook 実行中は、並行して別の Git コマンドを実行しない。

### 8) 事後確認

- `git status -sb` でコミット後の状態を確認する。
- 残りのコミット候補がある場合は、未コミット変更を再確認して 4) から 8) を次の候補に対して繰り返す。
- 事後確認も前の Git 操作の完了後に逐次行う。

## 出力フォーマット

```markdown
branch: <branch-name>
commit: <commit-hash>
message: <commit-subject>
body: yes|no
remaining: clean|<remaining summary>
notes: <only when needed>
```

## 返答のガイド

- 既定では文章で要約せず、上記フォーマットをそのまま最小限で返す。
- `notes` は補足が必要な場合のみ付け、不要なら省略する。
- `remaining` は作業ツリーが空なら `clean` と書く。
- 追加の確認が必要な場合のみ、フォーマットの後に短く具体的に質問する。
