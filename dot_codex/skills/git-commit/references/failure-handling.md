# 停止と失敗の扱い

`SKILL.md` の停止条件に当たった時、stage / commit / pre-commit hook が失敗した時、実行前に追加の権限が必要と分かった時に読む。

## 停止した時の対応

commit を作らず、次を報告する。

- 何が起きているか（detached HEAD、rebase 進行中、conflict、分割単位が不明、ファイル単位で分けられない）
- そのまま進めると何が壊れるか
- 解消するために人が取れる選択肢

**状況を自分で解消しない。** rebase の中断、conflict の解決、branch の切り替えは、いずれも人が意図を持って決めることで、commit skill の責務を超える。判断材料を揃えて返すところまでを行う。

## pre-commit hook

hook は失敗の種類で対応が変わる。

| hook の挙動 | 対応 |
| --- | --- |
| 検査だけ行い失敗（lint、型、secret 検出など） | 承認済み範囲で原因を直し、修正差分を確認してから明示 path で stage して commit し直す |
| ファイルを自動修正して失敗 | **修正差分を `git diff` で確認してから**再 stage して commit し直す |
| どの種類か判別できない | hook の出力を読み、判別できるまで再実行しない |

自動修正型で差分を確認せずに再 stage すると、hook が何を変えたか分からないまま commit することになる。整形のつもりで内容が変わっていても気づけない。

`--no-verify` で hook を迂回しない。hook は repo が合意した検査で、迂回すると commit 履歴に検査を通っていない変更が混ざる。

## 実行権限

作業指示と実行権限の許可は別。指示された段と対象を越える申請はしない。`Permission denied` という文字列だけでは sandbox 制限と断定せず、有効な権限情報、対象パス、ツールの結果から判断する。hook や署名の失敗も、一律に昇格対象へ分類しない。

| 状況 | 対応 |
| --- | --- |
| 通常の sandbox 制限と確認でき、正式な申請が可能 | 必要なコマンドと対象に限定して申請し、許可された場合に続行する |
| 明示的 deny、承認拒否 | 停止する。同じ結果を別コマンドや間接実行で得ようとしない |
| 承認後も権限エラーが続く | 停止する。追加の昇格を重ねない |
| 承認経路がない、または有効な方針で申請が禁止されている | 停止し、利用できない理由と残作業を引き継ぐ |
| 承認のタイムアウトやエラーで許可が成立しない | 許可済みと扱わず停止する。実行結果が不明なら、その点も報告する |
| sandbox 制限か他の原因か判断できない | 原因を確認するまで再実行・昇格申請をしない。確認できなければ引き継ぐ |

`workspace-write` でも `.git` は保護対象になり得る。worktree の `.git` が参照する Git ディレクトリも含め、有効な権限情報を確認する。必要性が実行前に分かる場合、失敗を一度起こす必要はない。

申請前に `git status -sb` と `git diff --staged` を読み直し、状態と対象が想定どおりか確認する。利用可能な実行ツールが対応している場合、`sandbox_permissions=require_escalated` と理由を指定する。チャットで先に昇格の再承認を求めず、正式な承認処理の審査・許可を受ける。Auto-review もこの審査を担うだけで、sandbox 制限を解除する包括許可ではない。

申請するのは具体的なコマンドだけとし、永続的な Git 許可ルールは提案しない。`git add` の許可を `git commit` の許可に流用しない。承認付きのツール呼出しで実行が成功した場合、同じコマンドをもう一度実行せず次の手順へ進む。

ACL 変更、管理者権限取得、sandbox 無効化を自動解決策にしない。push、履歴書換え、hook 省略へ切り替えることも認めない。

## 失敗時

- amend、squash、直接の ref 編集、その他の history 操作へ切り替えない。失敗の回避手段としてこれらを使うと、履歴が意図せず書き換わる。
- 条件を変えない retry は 1 回だけ、かつ**再実行で解ける見込みがある失敗**に限る。index lock の競合のように、他プロセスとの一時的な衝突が該当する。同じ権限・同じ条件で権限エラーを繰り返さない。hook 失敗や conflict も、原因を解消せず retry しない。
- 正式な承認を得た実行経路への切替と、hook の原因修正後の実行は、条件を変えない retry と区別し、それぞれ上の節に従う。
- retry する前に `git status -sb` と `git diff --staged` を読み直し、状態が想定どおりか確認する。
- retry しても失敗する場合は停止し、理由の要点を報告する。
