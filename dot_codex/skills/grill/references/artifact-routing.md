# Artifact Routing

問い詰める中で、どの doc / artifact に確定事項を反映するか迷う時だけ読む。

## 選び方

- 目的、成功条件、非目的、制約が曖昧: PRD
- `FR-*` ごとの要求や受入条件が曖昧: 要件定義
- 全体方針、責務分担、主要フローが曖昧: 基本設計
- インターフェース、処理フロー、検証・エラー処理、データ対応、考慮ケースが曖昧: 詳細設計
- 実装順序、変更境界、確認入口が曖昧: 実装計画
- 実装計画を `TASK-*` 単位へ落としたい: 実装計画の `タスク`
- 要件、タスクに対する確認観点を作りたい: テストケース
- 要件、設計、タスク、テストの対応漏れを見たい: traceability matrix
- 用語、文脈固有の呼び名、概念の関係が確定した: `CONTEXT.md`
- あとから変えるコスト、文脈なしの意外性、実際の trade-off がある判断: ADR

## 反映判断

- 既存 artifact が自然に受け止められるなら、そこへ最小追記する。
- 自然な置き場が明確で、依頼の流れ上必要なら新規 artifact を作ってよい。
- 置き場、artifact 種別、ID 体系、ADR lifecycle が曖昧なら、推測で作らず質問する。
- format 適用や複数 artifact の整合が必要なら `scribe` スキルを使う。
- 責務外の内容は対象 artifact に書かず、必要なら別 artifact の更新候補に分ける。
