# Requirements Heuristics

要件整理の迷いどころだけを扱う。必須ルールではない。

## まず疑うこと

- 依頼者が本当に困っているのは何か。
- その要求は手段であって、目的ではないか。
- 今回やらないことが曖昧なまま膨らんでいないか。
- 成功条件が「なんとなく良くなる」になっていないか。

## 整理したい項目

- 背景
- 課題
- 目的
- 受入条件
- 非目的
- 前提・制約
- 優先順位（必要な場合だけ）
- 未確認事項

優先順位は合意に必要な場合だけ扱い、format の必須項目にはしない。

## 確認を先に置くべき場面

- 複数の解決方向がありそう。
- ユーザーごとに期待する受入条件が違いそう。
- 互換性や運用制約でスコープが大きく変わる。
- 実装前に合意しないと手戻りが大きい。

## 避けたい兆候

- 目的より先に UI や実装方式を決めている。
- 非目的がなく、際限なく広がる。
- 必須と任意が分かれていない。
- 未確認事項を隠したまま技術計画へ進んでいる。
- 実装タスクの箇条書きが、そのまま要件の代わりになっている。
