# Lapidary

変更を commit できる状態まで仕上げる。目的は、指摘を並べることでも、拾ったものを全部直すことでもなく、commit してよい状態にすること。

## 手順

1. `git status -sb`、`git diff`、`git diff --staged` で変更の全体を読む。git-commit から範囲を渡された時は、その範囲を読む。
2. 4 つの観点をすべて通す。観点ごとに、何を確かめて何が無かったかを持つ。
3. 拾ったものごとに「直さないと、誰のどの判断や動作が変わるか」を 1 文で言えるか確かめる。言えないもの（言い回しの好み、同じ意味の別表現）は落とす。
4. 残ったものを直す。直すのは自分が加えた変更だけ。ユーザー自身の編集と、`AGENTS.md` の「確認してから進めること」に当たる箇所は、直さずに報告する。未 commit の編集を上書きすると、git に控えが無い。
5. 直した箇所に関係する観点だけ確かめ直す。直しが lint、test、build の結果を変えうるなら、それも通し直す。新しい指摘が出たら手順 3 へ戻る。
6. 「出力」に従って返す。

終わりを決めるのは、4 つの観点を通し切ったことだけ。「もう 1 周すれば何か出る」は常に言えるので、回数は根拠にしない。

## 観点

### スコープ

- 変更した行を 1 つずつ依頼に対応付け、依頼を 1 つずつ変更に対応付ける。対応先を言えない行（頼まれていない変更）と、手を付けていない依頼（TODO、仮実装、通していない検証）を挙げる。
- 性質の違う変更が混ざっていたら、commit を分けるよう返す。
- 検証はここで実行しない。済んでいるかだけを確かめ、未実行なら見直しを止めて検証へ戻す。

### 事実

- 断定を 1 つずつ根拠（ファイル、差分、コマンドの結果、公式 docs、既存の doc）に当てる。当てられないものを挙げる。
- 強い語（「できない」「必ず」「〜が原因」）だけでなく、`X の Y` を `X` に、`〜の場合がある` を `〜する` に広げる一段の拡張も見る。
- 推論を断定の形で書いていないか。実測値に、いつ何を数えた値かが付いているか。

### 整合

- 変えた path、名前、設定キー、引用した文言、数えた値を `rg` で検索し、古いまま残っている場所を挙げる。本文を直すと、それを引用・要約している場所が黙って古くなる。
- 参照（リンク、path、関数名）を 1 つずつ辿り、空振りしないか確かめる。1 つの概念に 1 つの語を使っているか。

### 過剰さ

読み手が理解や判断に使わない部分。長さではなく、判断に効くかで見る。

- doc と文章: 同じ情報を 2 箇所以上に書いていないか（言い換え、節名と 1 文目、正本がある内容の写しを含む）。消しても読み手の判断が変わらない記述が無いか。
- コード: 頼まれていない抽象、標準機能や既存の依存で足りる自前の実装、消しても振る舞いが変わらないコードが無いか。入力の検証、権限の境界、timeout、失敗時の後始末と復旧は、過剰さに数えない。

## 組み込みの review を提案する条件

この skill は agent を起動しない。次に当たる時だけ、報告の最後で `/review` を提案する。走らせるかはユーザーが決める。ユーザーが「じっくり見て」と言った時は、提案を挟まず走らせる。

- 正しさへの影響が大きい。データの変換、並行処理、境界条件、失敗時の処理、公開 IF。commit の前に「Review uncommitted changes」で見る。
- 権限、認証、秘密情報、外部入力、hook、CI、agent の設定に触れた。「Custom review instructions」で security の観点を指定する。

doc の追従が要りそうな変更（使い方、設定、公開挙動を変えた）なら、scribe を通すよう一言添える。

## 出力

短く返す。毎回の commit の前に出るので、長いと読まれない。

- 指摘が無い時: 観点ごとに、何を確かめたかを 1 行ずつ。
- 指摘がある時: 直したもの、直さずに残したもの（理由付き）、commit できるかどうか、提案する組み込みの review。直したものは commit にそのまま入るので、ユーザーが見落とさないように分けて書く。

秘密情報にあたる値は報告に写さない。値ではなく、どのファイルのどの箇所かを書く。
