# Artifact Workflows

計画作成で扱う成果物の選び方と作り方。
この文書は、どの成果物を作るか、何を含めるかで迷う時だけ読む。

## 選び方

- 目的、成功条件、非目的、制約が曖昧: PRD
- `FR-*` ごとの要求や受入条件が曖昧: 要件定義
- 全体方針、責務分担、主要 flow が曖昧: 基本設計
- interface、処理 flow、validation、data mapping、edge case が曖昧: 詳細設計
- 実装順序、変更境界、検証入口が曖昧: 実装計画
- 実装計画を `TASK-*` 単位へ落としたい: 実装計画の task section
- 要件、設計、task に対する確認観点を作りたい: テストケース
- PRD、要件、設計、task、test の対応漏れを見たい: traceability matrix

## 共通手順

- 対象 artifact と根拠資料を確認する。
- 対象 scope と non-scope を短く言い換える。
- 既存 ID があれば継続し、ID 体系が未確定なら採番前に確認する。
- 質問は 1 つずつ行い、推奨回答を添える。
- 受入条件、検証、期待結果は観測可能な結果で書く。
- Open Questions は未確認事項だけに使い、確認済み前提を混ぜない。
- docs を更新する時は、対象 format reference を読む。

## PRD

- 背景、問題、目的、成功条件、scope、non-goals、制約を整理する。
- 個別 feature の詳細要件は要件定義に寄せる。
- ぼんやりした依頼では、まず「何が満たされれば成功か」を固める。

## 要件定義

- PRD や会話で出た実現したい要件を、`FR-*` 単位で扱える粒度へ整理する。
- 要求、受入条件、非範囲、依存、制約を分ける。
- 要件が固まったら、基本設計へ進める。

## 基本設計

- 要件、受入条件、制約をもとに、全体方針と責務分担を整理する。
- 詳細な処理順や実装手順は入れすぎず、詳細設計へ送る。
- 代替案は、実際に検討価値がある場合だけ残す。

## 詳細設計

- 基本設計をもとに、実装計画へ渡せる粒度まで処理と interface を詰める。
- interface、processing flow、validation、data mapping、edge cases を分ける。
- 変わりやすい code snippet は、判断を明確にする時だけ短く使う。

## 実装計画と task

- 詳細設計から、実装スライス、変更境界、検証入口、リスクを整理する。
- task は小さく、完了条件と確認方法が見える粒度にする。
- task 間の依存順を明示する。
- 実装結果、日報、作業ログは混ぜない。

## テストケース

- 自動テスト可能、手動確認が必要、確認不能または費用対効果が低いものを分ける。
- test case は `TC-*` 単位で、前提、手順、期待結果、対応する `AC-*` / `TASK-*` を持たせる。
- test code を作る場合は、既存 test placement、命名、実行入口を確認する。
- TDD が難しい対象では、手動確認、比較観点、最小再現 artifact などを先に置く。

## Traceability Matrix

- `FR-*`、`REQ-*`、`AC-*`、`BD-*`、`DD-*`、`TASK-*`、`TC-*`、test code の対応を整理する。
- 対応が確認できないものは推測で埋めず、`TBD` または `N/A` と理由を残す。
- 要件に設計、task、test がない場合は漏れとして分ける。
- 設計、task、test が要件に紐付かない場合は孤立として分ける。
