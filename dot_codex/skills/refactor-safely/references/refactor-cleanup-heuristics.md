# Refactor Cleanup Heuristics

`refactor-safely` 本文だけでは判断しづらい、削除系リファクタ向けの補助資料。
ここに書く内容は標準手順の追加ではなく、迷ったときの確認観点。

## まず見ること

- その削除や統合は、今回の依頼範囲に本当に含まれているか。
- 近傍実装に、残すべき既存パターンや命名規約がないか。
- 回帰確認の手段を、削除前に決められているか。
- 根拠が弱い場合に、保留へ戻せる分割になっているか。

## リスク分類の目安

### `SAFE`

- 未使用 import
- 内部限定の未使用関数、型、定数
- 呼び出し元が明確に存在しない private helper
- 削除対象が静的検索で追いやすく、公開境界に触れないもの

### `CAREFUL`

- 動的 import や設定値から参照される可能性があるもの
- 文字列キー、テンプレート、フック名、コマンド名で間接参照されるもの
- 生成物やテンプレート展開の入力になっている可能性があるもの
- 実行時にしか現れない経路で使われる可能性があるもの

### `RISKY`

- 公開インターフェースの一部
- 複数箇所から共有されるユーティリティや基盤コード
- 永続化、認証認可、権限、設定読み込み、運用手順に近いもの
- 利用実績は薄く見えても、失敗時の影響が大きいもの

## 対象別の確認観点

### 未使用 import / export

- 静的参照が本当にないか。
- re-export や barrel 経由で公開されていないか。
- 型だけの利用、テンプレート内の利用、設定ファイルからの参照がないか。

### 未使用 file

- 単純な import 参照だけでなく、生成、テンプレート、手動運用で参照されていないか。
- README、スクリプト、CI、dotfiles の適用手順などに登場しないか。
- 名前で grep しても出ない場合だけでなく、役割単位でも確認できるか。

### 未使用 dependency

- コード上の import がなくても、CLI、スクリプト、テンプレート、ビルド、CI で使われていないか。
- 直接依存ではなく、設定やフックから呼ばれていないか。
- 削除後の build / lint / test で回帰確認できるか。

### 重複コード

- 見た目が似ているだけで、責務や呼ばれ方が違わないか。
- どちらを残すかは、既存文脈への整合、責務の明確さ、利用実績、検証実績で決める。
- 共通化で引数や分岐が増えすぎるなら、無理に統合しない。

## 疑うべき場面

- grep では未使用に見えるが、名前が運用手順やテンプレートに現れる。
- 静的参照はないが、設定値や文字列から読まれていそう。
- 共有基盤コードで、近傍の影響範囲が広い。
- 「きれいになる」以外の削除根拠が弱い。
- 重複解消のために、新しい抽象化や設定層を足したくなっている。

## 任意の補助ツール例

- `knip`
- `depcheck`
- `ts-prune`

これらは、使える環境なら補助的に使ってよい。
ただし、この repo の標準前提にはせず、ツール結果だけで削除を確定しない。
