# Request Shaping Templates

`request-shaping` で迷ったときの補助資料。
ここでは、依頼を実装ブリーフへ整えるための短い型だけを扱う。

注意:

- これはユーザーへの必須入力テンプレートではなく、`request-shaping` が依頼を整形するときの出力例。
- ユーザーの依頼に項目が足りなくても、会話から補えるものは補い、重要な未確定事項だけを残す。

## 基本テンプレート

```markdown
## 目的

- [今回の主題を一文で]

## 確認済み事実

- [確認済みの事実]

## 制約

- [触ってよい範囲、避けたい変更、期限、互換性]

## 完了条件

- [どうなれば今回は十分か]

## 非目的

- [今回はやらないこと]

## 仮定

- [会話から暫定補完した前提]

## 未確定事項

- [高リスクな不明点]

## 次アクション

- [次に何をそろえるか]

## 次に使うスキル

- [task-intake / workspace-intake / plan-product / session-orchestrator / plan-architect]
```

使い分けの目安:

- 依頼の対象を軽く固定したいなら `task-intake`
- 事実ベースで探索へ進みたいなら `workspace-intake`
- 目的や成功条件の整理がまだ重いなら `plan-product`
- 長めの作業の進め方を切りたいなら `session-orchestrator`
- 実装順序や影響範囲を技術計画として詰めたいなら `plan-architect`

## 良い整形の例

- 要望が3つあっても、今回の主題は1つに縮める。
- 「多分」「おそらく」は事実欄へ置かず、仮定や未確定事項へ送る。
- 非目的を先に置き、ついで作業を本件へ混ぜない。

## 避けたい整形

- 技術解を先に決め打ちして、目的が見えなくなる。
- 背景説明だけ長く、完了条件が空になる。
- 不明点を埋めずに断定口調で次工程へ渡す。
