# Artifact Workflows

doc / artifact の作り方や含める内容で迷う時だけ読む。
どの artifact が必要かの選択で迷う時は、`grill` の [artifact routing](../../grill/references/artifact-routing.md) を読む。

## 共通手順

- 対象 artifact と根拠資料を確認する。
- 対象スコープと非スコープを短く言い換える。
- 既存 ID があれば継続し、ID 体系が未確定なら採番前に確認する。
- 受入条件、確認方法、期待結果は観測可能な結果で書く。
- `未確認事項` は未確認事項だけに使い、確認済み前提を混ぜない。
- docs を更新する時は、対象 format reference を読む。

## PRD

- 概要、課題、目的、成功条件、スコープ、非目的、制約を整理する。
- 個別 feature の詳細要件は要件定義に寄せる。
- ぼんやりした依頼では、まず「何が満たされれば成功か」を固める。

## 要件定義

- PRD や会話で出た実現したい要件を、`FR-*` 単位で扱える粒度へ整理する。
- 要求事項、受入条件、非目的、前提・制約を分ける。
- 要件が固まったら、基本設計へ進める。

## 基本設計

- 要件、受入条件、制約をもとに、全体方針と責務分担を整理する。
- 詳細な処理順や実装手順は入れすぎず、詳細設計へ送る。
- 代替案は、実際に検討価値がある場合だけ残す。

## 詳細設計

- 基本設計をもとに、実装計画へ渡せる粒度まで処理とインターフェースを詰める。
- インターフェース、処理フロー、検証・エラー処理、データ対応、考慮ケースを分ける。
- 変わりやすい code snippet は、判断を明確にする時だけ短く使う。

## 実装計画とタスク

- 詳細設計から、実装スライス、変更境界、確認入口、リスクを整理する。
- タスクは小さく、完了条件と確認方法が見える粒度にする。
- タスク間の依存順を明示する。
- 実装結果、日報、作業ログは混ぜない。

## テストケース

- 自動テスト可能、手動確認が必要、確認不能または費用対効果が低いものを分ける。
- テストケースは `TC-*` 単位で、前提条件、手順、期待結果、対応する `AC-*` / `TASK-*` を持たせる。
- テストコードを作る場合は、既存の配置、命名、実行入口を確認する。
- TDD が難しい対象では、手動確認、比較観点、最小再現 artifact などを先に置く。

## Traceability Matrix

- `FR-*`、`REQ-*`、`AC-*`、`BD-*`、`DD-*`、`TASK-*`、`TC-*`、テストコードの対応を整理する。
- 対応が確認できないものは推測で埋めず、`TBD` または `N/A` と理由を残す。
- 要件に設計、タスク、テストがない場合は漏れとして分ける。
- 設計、タスク、テストが要件に紐付かない場合は孤立として分ける。
