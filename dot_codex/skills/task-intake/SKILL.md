# Task Intake

高品質なバイブコーディングのための、軽量な入口整理スキル。
目的は、探索の前に「今回どこまでを扱うか」を短くそろえること。

## 前提

- [AGENTS.md](../../AGENTS.md) の共通品質原則と既定フローを前提に適用する。
- とくに `スコープを最小に保つ`、`単純さを優先する (KISS)`、`不確実さを隠さず確認する` を強く意識する。

## 目的

- 日常的な曖昧依頼を、探索可能な最小単位へ整える。
- いきなり重い要件整理や技術計画へ進むのを避ける。
- 今回扱うこと、扱わないこと、今すぐ確認が必要なことを切り分ける。
- `目的 / 確認済み事実 / 制約 / 完了条件` を入口としてそろえ、今回の停止線を置く。

## 対象

- 相談、壁打ち、軽い改善依頼、方向性確認。
- 目的はあるが、対象や成功条件がまだ粗い依頼。
- まず何を探索すべきかをそろえたい依頼。

## 対象外

- 目的、成功条件、非目的、制約を詳しく整理すべき依頼。
- 具体的な実装順序や影響範囲の整理が主目的の依頼。
- そのまま実装へ入れるほど具体的な依頼。

## 優先順位

判断が衝突したら、次の順で優先する。

1. ユーザーの目的、制約、成功条件
2. 既存仕様や運用上の前提
3. [AGENTS.md](../../AGENTS.md) の共通品質原則と、このスキルの依頼整理適用

## 重視すること

### 1) まず依頼の主語を揃える

- 依頼を短く言い換え、何を前に進めたい相談かを明確にする。
- 背景を広げすぎず、今回の相談に直接効く部分だけ拾う。

### 2) 制約、成功条件、非目的を軽く固定する

- いま見えている制約を短く置く。
- 今回どうなれば十分かを短く置く。
- 今回やらないことを先に分け、スコープの膨張を防ぐ。

### 3) 不明点を残したままでも前に進める形にする

- いま確認が必要な不明点と、後回しでよい不明点を分ける。
- 認証、権限、秘密情報、破壊的操作に関する不明点は入口段階で確認する。
- 安全境界が未確定な場合は、探索前に確認事項として切り出す。

### 4) 設計判断へ飛びすぎない

- この段階では、実装案や技術案を広げない。
- まずは探索へ進める最小の対象と停止線だけを置く。

### 5) 重い整理へ飛びすぎない

- まずは `workspace-intake` に渡せる粒度で止める。
- 優先順位や制約の整理が重いなら `plan-product` へ渡す。
- 実装順序や影響範囲の整理が必要なら `plan-architect` へ渡す。

## 使い分け

- 軽い入口整理で足りるときは、この `task-intake` を使う。
- 探索対象を固める段階では `workspace-intake` へ進む。
- 目的、成功条件、非目的、制約まで固める必要があるときは `plan-product` へ進む。
- 実装順序や影響範囲を詰める段階では `plan-architect` へ進む。

## 出力ガイド

- 次の項目を簡潔に整理する。
  - 目的
  - 確認済み事実
  - 制約
  - 今回の対象
  - 成功条件
  - 非目的
  - すぐ確認が必要な点
  - 次に探索すべきもの
  - 次に使うべきスキル
- 出力は軽く止め、長い仕様書にしない。
- 仮定がある場合は、確定事項と分けて扱う。
