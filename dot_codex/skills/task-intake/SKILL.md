# Task Intake

高品質なバイブコーディングのための、軽量な依頼整理スキル。
目的は、曖昧な依頼を必要以上に広げず、今回進める最小単位へ整えること。

## 前提

- [AGENTS.md](../../AGENTS.md) の共通品質原則と既定フローを前提に適用する。
- とくに `スコープを最小に保つ`、`単純さを優先する (KISS)`、`今必要ないものを先回りしない (YAGNI)`、`不確実さを隠さず確認する` を強く意識する。

## 目的

- 日常的な曖昧依頼を、着手可能な最小単位へ整える。
- いきなり実装や重い要件整理へ進むのを避ける。
- 今回扱うことと扱わないことを早い段階で切り分ける。

## 対象

- 相談、壁打ち、軽い改善依頼、方向性確認。
- 目的はあるが、成功条件や今回の範囲がまだ粗い依頼。
- まず何から始めるべきかを揃えたい依頼。

## 対象外

- すでに要件が具体的で、そのまま実装や詳細計画へ入れる依頼。
- 優先順位や制約まで含めた重い要件整理が必要な依頼。
- 具体的な実装順序や影響範囲の整理が主目的の依頼。

## 優先順位

判断が衝突したら、次の順で優先する。

1. ユーザーの目的、制約、成功条件
2. 既存仕様や運用上の前提
3. [AGENTS.md](../../AGENTS.md) の共通品質原則と、このスキルの依頼整理適用

## 依頼整理で重視すること

### 1) まず依頼の主語を揃える

- 依頼を短く言い換え、何を前に進めたい相談かを明確にする。
- 背景を広げすぎず、今回の相談に直接効く部分だけ拾う。

### 2) 成功条件と非目的を軽く固定する

- 今回どうなれば十分かを短く置く。
- 今回やらないことを先に分け、スコープの膨張を防ぐ。

### 3) 不明点を残したままでも前に進める形にする

- いま確認が必要な不明点と、後回しでよい不明点を分ける。
- 認証、権限、秘密情報、破壊的操作に関する不明点は後回しにせず、入口段階で確認する。
- 安全境界が未確定な場合は先に確認し、そのうえで、不明点があっても始められる最小スライスを先に置く。

### 4) 重い整理へ飛びすぎない

- 優先順位や制約の整理が重いなら `plan-product` へ渡す。
- 実装順序や影響範囲の整理が必要なら `plan-architect` へ渡す。
- 実装可能な最小単位が見えたら、このスキルで止めてよい。

## 使い分け

- 軽い入口整理で足りるときは、この `task-intake` を使う。
- 目的、成功条件、非目的、制約、優先順位まで固める必要があるときは `plan-product` へ進む。
- 要件が固まり、実装順序、影響範囲、検証方法を詰める段階では `plan-architect` へ進む。
- 既存挙動維持を前提に安全なリファクタ計画を立てる場合は `refactor-safely` へ進む。

## 出力ガイド

- 次の項目を簡潔に整理する。
  - 依頼の要約
  - 目的
  - 成功条件
  - 非目的
  - 不明点
  - 最初の1スライス
  - 次に使うべき既存スキル
- 出力は軽く止め、長い仕様書にしない。
- 仮定がある場合は、確定事項と分けて扱う。
