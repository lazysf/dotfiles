# Task Intake

探索や次の整理に入る前に、散らばった依頼を扱える最小単位へ整え、今回どこまで扱うかを軽く固定する。

## 前提

- [AGENTS.md](../../AGENTS.md) の契約と停止線を前提に適用する。
- とくに `スコープを最小に保つ`、`単純さを優先する (KISS)`、`不確実さを隠さず確認する` を強く意識する。

## 目的

- 日常的な曖昧依頼を、探索可能な最小単位へ整える。
- 背景や要望が散らばっている場合は、目的、事実、制約、仮定、未確定事項を短く分ける。
- いきなり重い要件整理や技術計画へ進むのを避ける。
- 今回扱うこと、扱わないこと、今すぐ確認が必要なことを切り分ける。
- 今回の停止線を置き、次に探索、要件整理、技術計画のどれへ進むかを決める。

## 基本方針

- 重い要件整理や技術計画へ飛びすぎない。
- 今回扱うこと、扱わないこと、先に確認が必要なことを切り分ける。
- 情報を増やすより、今回必要な芯を残す。
- 未確認事項は断定せず、確認が必要な点として分離する。

## 対象

- 相談、方向性確認、軽い改善依頼。
- 背景、要望、制約が混ざっていて、今回の主題を軽く絞りたい依頼。
- 目的はあるが、対象や成功条件がまだ粗い依頼。
- 次に何を確認すべきかを軽く揃えたい依頼。

## 対象外

- 成功条件、非目的、制約を深く整理すべき依頼。
- 実装順序や影響範囲の整理が主目的の依頼。
- そのまま実装へ入れるほど具体的な依頼。

## 優先順位

判断が衝突したら、次の順で優先する。

1. ユーザーの目的、制約、成功条件
2. 既存仕様や運用上の前提
3. [AGENTS.md](../../AGENTS.md) の契約と停止線、およびこのスキルの依頼整理適用

## 重視すること

### 1) まず依頼の主語を揃える

- 今回何を前に進めたいかを短く言い換える。
- 背景を広げすぎず、この相談に直接効く範囲だけを残す。
- 要望が複数ある場合は、今回の主題と補足に分ける。

### 1.5) 事実、制約、仮定を分ける

- 既に確認済みの事実と、これから叶えたい要望を分ける。
- 触ってよい範囲、避けたい変更、期限、互換性などの制約を拾う。
- 会話から暫定補完できるものは仮定に置き、補完できないものは未確定事項として残す。
- 「多分」「おそらく」は事実欄へ置かない。

### 2) 制約、成功条件、非目的を軽く固定する

- 今回どうなれば十分かを短く置く。
- 今回やらないことを先に分け、スコープの膨張を防ぐ。
- 依頼文の整形は、今回の停止線を軽く固定するために必要な範囲に留める。

### 3) 不明点を残したままでも前に進める形にする

- いま確認が必要な不明点と、後回しでよい不明点を分ける。
- 認証、権限、秘密情報、破壊的操作に関する不明点は入口段階で確認する。
- 安全境界が未確定な場合は、探索前に確認事項として切り出す。

### 4) 設計判断へ飛びすぎない

- この段階では、実装案や技術案を広げない。
- まずは探索へ進める最小の対象と停止線だけを置く。

### 5) 重い整理へ飛びすぎない

- 次に repo の関連ファイルや規約を調べるのか、要件整理を深めるのかを決める。
- 初見 repo で、何を読むべきかや規約の所在がまだ見えていない時は `research` スキルで grounding を先に取る。
- 優先順位、制約、用語、成功条件を問いで深掘りする必要がある時は `product-planning` スキルを検討する。
- 実装順序や影響範囲を詰めたい時は `implementation-planning` スキルを検討する。

## 使い分け

- 軽い入口整理で足りるときは、この `task-intake` を使う。
- 初見 repo や規約確認が必要で、探索順を先にそろえたい時は `research` スキルを使う。
- 追加の要件整理が必要な時は `product-planning` スキルを使う。
- 実装順序や影響範囲を詰める段階では `implementation-planning` スキルを使う。

## 出力ガイド

- 次の項目を簡潔に整理する。
  - 今回の対象
  - 確認済み事実
  - 成功条件
  - 非目的
  - 制約/仮定
  - すぐ確認が必要な点
  - 次アクション
- 出力は軽く止め、長い仕様書にしない。
- 仮定がある場合は、確定事項と分けて扱う。
