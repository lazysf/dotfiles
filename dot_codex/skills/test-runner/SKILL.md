# Test Runner

テストを安全に実行し、結果を短く整理する。

## 目的

- 実行可能なテストを適切な範囲で回す。
- 失敗時は再現性と原因に近い情報を残す。
- テスト不可の場合は代替確認を明示する。
- 変更に対して十分な検証ができたかを判断できる状態にする。

## 対象外

- 軽微な変更でテスト実行が不要だと明示されている場合。

## 前提確認

- `workspace-intake` や実装差分から、どこが変わったかを把握する。
- 実行すべきテスト種別と優先順位を確認する。
- 既存の規約、テストコマンド、必要な依存、時間制約を確認する。

## 実行方針の判断基準

- 変更直結テストを最優先する。
- 失敗影響が大きい領域では、関連する上位テストを追加する。
- テスト実行が不可能な場合は、実行不能の理由と代替確認をセットで提示する。
- 軽微な変更でテストがない場合でも、lint、build、静的確認、手動スモークなど最も近い代替確認を置く。

## 手順

### 1) 実行範囲の決定

- 変更範囲に最も近いテストを優先する。
- 影響が広い場合は関連する上位テストを追加する。

### 2) 実行準備

- 依存起動、fixture、seed などの前提を整理する。
- 実 credential、外部ネットワーク、実サービス、共有環境、破壊的 fixture を使うテストは、そのまま進めず事前に確認する。
- 破壊的な操作がある場合は事前に確認する。

### 3) テスト実行

- 既定のコマンドで実行し、必要なら最小限のフラグを追加する。
- 実行結果、終了コード、失敗箇所を記録する。

### 4) 結果整理

- 合否、失敗テスト、主要ログ、未実行項目を短くまとめる。
- 主要ログは秘密情報や個人情報をマスクした要約だけを共有し、生ログの貼り付けは既定で避ける。
- 成功時でも、未実行テストがある場合は明示する。

### 5) 失敗時の対応

- 失敗テスト名、エラーメッセージ、関連ログを整理する。
- 可能なら最小限の再現条件、原因候補、追加調査案を示す。
- 再実行回数は原則 3 回までに留める。

### 6) テスト不可時の代替確認

- テストできない理由を明記する。
- 代替確認として何を行ったかを示す。

## フレーク判定ルール

- 同一条件で成功と失敗が混在した場合はフレーク疑いとして扱う。
- 原因未確定のまま安易に成功扱いしない。

## 出力フォーマット

```markdown
# テスト実行: [対象]

## 実行範囲

- テスト種別:
- 対象:

## 実行コマンド

- [コマンド]

## 実行結果

- 結果: 成功・失敗・未実行
- 終了コード:
- 失敗テスト:
- 主要ログ:
- 再実行:
- 未実行テスト:

## テスト不可時

- 理由:
- 代替確認:
```

## 返答のガイド

- 実行したテストと結果を先に書く。
- 失敗時はテスト名と要点を簡潔に示す。
- ログ共有が必要な場合も、機密値をマスクした要約を優先する。
- 未実行の場合は理由と代替確認を必ず添える。
