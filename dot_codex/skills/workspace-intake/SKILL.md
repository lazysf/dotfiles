# Workspace Intake

高品質なバイブコーディングのための、探索専用スキル。
目的は、依頼整理のあとに「この依頼に対して何を読めばよいか」を事実ベースで固めること。

## 前提

- [AGENTS.md](../../AGENTS.md) の既定フローを前提に適用する。
- `task-intake` で今回の対象が軽く定まっていることを想定する。

## 目的

- 既存規約、関連ファイル、近傍実装、テスト入口を把握する。
- 何を読めば判断材料が揃うかを最小範囲で定める。
- 探索と要件整理、探索と設計判断を混ぜない。

## 対象

- 初見または不慣れなリポジトリでの修正依頼。
- 既存規約や近い実装を先に把握したい依頼。
- `task-intake` 後に、次にどこを見るべきかを固めたい依頼。

## 対象外

- 要件や成功条件そのものを詰める依頼。
- 実装順序や変更単位を決める依頼。

## 読む順番

1. `AGENTS.md`
2. README や運用文書
3. 主要設定、マニフェスト、CI、lint、formatter
4. 関連ディレクトリと近傍実装
5. テスト入口、実行コマンド、確認手段

## 重視すること

### 1) まず規約を拾う

- リポジトリ全体の明示規約を先に確認する。
- その依頼で従うべきローカルルールを優先して拾う。

### 2) 近い実装を探す

- 同じ責務、同じ層、同じ入出力を扱う実装を優先する。
- 遠い一般論より、近い既存パターンを優先する。

### 3) 実行手段を把握する

- テスト、build、lint、スモークなど、何が確認手段になるかを把握する。
- 実行できない場合も、その理由が見えるところまで確認する。

### 4) 探索を広げすぎない

- 依頼達成に必要な範囲だけ読む。
- いきなり全体理解を目指さない。

## 出力ガイド

- 次の項目を簡潔に整理する。
  - 依頼要約
  - 探索対象
  - 既存規約
  - 近い実装
  - 確認済みの実行手段
  - 最初の着手単位
- 要件確定や設計判断までは踏み込まない。
